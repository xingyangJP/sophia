## このプロジェクトは何か

**一人のためのAIを作る。**

いまのAIは1億人に向けて作られている。だから**世界を全部知っていなければならず**、
**誰に読まれても安全な言い方をしなければならない。** その2つがエネルギーを食っている。

**Sophia は相手を一人に固定する。** すると両方とも要らなくなる。

| 1億人に向けると | 一人に向けると |
|---|---|
| 世界を全部知っている必要がある | **事実は外から取ればいい**（ウェブ検索） |
| 誰にでも安全な言い方が要る | **その人の閾値に合わせればいい** |
| **その結果、モデルは大きくなり続ける** | **中に持つのは「その人のこと」だけ。それは小さい** |

> **少ないエネルギーで会話が成り立つのは、モデルが世界を知っているからではなく、
> その人を知っているからである。**

これが**仮説の起点**であり、**1/1000 のエネルギーはその帰結**である。 —
[docs/VISION.md](docs/VISION.md) / [docs/PHILOSOPHY.md](docs/PHILOSOPHY.md)

### 何を作っていないか —— **神を作ろうとしていない**

**いまのAIの進歩は「モデルの中に世界の事実をどれだけ詰め込めるか」の競争になっている。**
詰め込むほど賢くなり、エネルギーは青天井になる。**Sophia はその競争に参加しない。**

**賢さで勝つのではなく、その人にとって要らないものを持たないことで勝つ。**

| 何を | どこに置くか | 毎ターンの費用 |
|---|---|--:|
| **世界の事実**（変わる・膨大・その人と無関係） | **外に置き、要るときだけ取る** | 取ったときだけ |
| **その人のこと**（変わらない・少量・その人そのもの） | **重みに焼く** | **0** |
| **言い方・行間** | その人専用の翻訳層（0.5〜1.5B） | 推論1回 |

### 難所は賢さではなく **匙加減**

**「バカに見える」には2種類あり、片方だけを潰すともう片方に落ちる。**

| | どう見えるか |
|---|---|
| **嘘**（知らないことを、相手が聞きたい形で断言する） | **一度バレたら全部信用できなくなる** |
| **逃げ**（「一般には〜と言われていますが、状況によります」） | **正しいが、使えない。これも十分バカに見える** |

**汎用モデルが逃げるのは、1億人に対して安全な言い方を1つ選ばなければならないからである。**
安全側の但し書き・一般論の前置き・断定を避ける言い回しは、**知らない相手に対する保険料**であり、
**相手が一人だと分かっていれば、その保険料は返せる。トークンでも、エネルギーでも。**

**そして根拠が無ければ、嘘と逃げは両立しない。**
根拠を持たないモデルに「嘘をつくな」とだけ言えば、**逃げるしかなくなる。**
**検索は、断言してよい根拠を取りに行く仕組みである**（だから結果は出典を伴う）。

> **詳細は [docs/PHILOSOPHY.md](docs/PHILOSOPHY.md)。これは哲学と数学のプロジェクトである。**

### プライバシーは、目的ではなく構造から出てくる

**このプロジェクトの出発点は、たしかにプライバシーだった。**
生成AIを業務で使うとき、社内文書・顧客情報・未公開のソースコードを外部APIに投げる判断がしにくい ──
**その制約を外すために、ローカルで完結するアプリを作り始めた。**

**いまの主張はその先にある。** 一人のために端末の中で完結させれば、**外に出す理由がほとんど残らない。**
プライバシーは**守るべき制約**としてではなく、**設計の帰結**として付いてくる。

> **外部へ出てよいものは2つだけ**（NFR-01 / 2026-08-23 改定）── **モデルの取得と更新確認**、および
> **利用者が検索を有効にした会話で、モデルが組み立てた検索語**。
> **会話本文・履歴・ファイルの中身・利用者像は出さない。**
> 検索語は**送信前に画面へ表示し、監査ログへ記録する**。

### 2つのトラック

| | 内容 |
|---|---|
| **A. アプリ（器）** | **一人に合わせて調整できる器**を macOS ネイティブ（SwiftUI + MLX）で作る。**他人にも配布できる単体アプリ**として仕上げる |
| **B. モデル（中身）** | **その人のための重み**を作る。汎用の賢さを追うのではなく、**その人を知っている状態**を重みに持たせる。ローカルで着手し、上限に達したらクラウドへ移行する（**学習のみ。推論はローカルを維持する**） |

> **⚠ 2026-08-23 訂正: 両者はもう独立していない。**
> かつては「接点はモデルファイル1個だけで、どちらかの完成をもう一方が待たない」と書いていた。
> **パーソナライズが両者を繋ぐ** ── 利用者の訂正を拾って重みへ焼く経路は**アプリの中にある**（FR-27・FR-31）。
> **器が中身を作る。** その意味で、A は B の前提である。

> **検索（FR-30）は「モデルを作ること」の代替ではなく、その前提である。**
> かつてここには「RAG は目的Bの代替にならない。補助機能として将来検討」と書いていたが、
> **枠が違っていた** ── 検索は外付けの代用品ではなく、**「事実は外・その人は中」というアーキテクチャの片側**である。
> **事実を外に出すからこそ、重みをその人のために空けられる。**

### 実測されている性能 ─ 開発用バックエンド（Ollama + GGUF / M3 · 16GB）

| モデル | 用途 | 生成速度（冷間 → 連続使用時） |
|---|---|---|
| `sophia-chat`（qwen3:8b） | 日本語の文章作成 | 13.4 → **7.0** tok/s |
| `sophia-coder`（qwen2.5-coder:7b） | コーディング支援 | 14.1 → **9.0** tok/s |

### アプリ（MLX / Qwen3-8B-4bit）─ 2往復ぶんのみ・Debug ビルド

**計測経路は通ったが、取れているのは連続2往復だけ。基準値として使える精度ではない。**

| 項目 | 1往復目 | 2往復目 |
|---|--:|--:|
| 生成速度（decode） | 19.46 tok/s | **19.21 tok/s** |
| **プリフィル** | 123.26 tok/s | **13.39 tok/s** |
| 最初の1文字まで（TTFT） | 0.97秒 | **11.87秒** |
| **本文**の1文字目まで（TTFR） | 7.71秒 | 28.36秒 |
| ピークメモリ | 4,615 MB | 4,656 MB |

> **⚠️ 2往復目でプリフィルが崩れ、TTFT が 0.97秒 → 11.87秒 になっている。**
> **NFR-03（1秒以内に何かが出る）は2往復目で破れている。**

### 分かっていること ─ 実は**アプリの必要量は約4.6GB**（9GB説は撤回）

**アプリが生成中に必要とするのは、重み 4,394 MiB ＋ フォワードの一時 約226MB ＝ 約4.6GB。**
**16GB機にとって無理な量ではない。**

> **⚠️ 2026-08-17、一度「約9GB」と結論して撤回した。**
> あれは**計測ハーネスの欠陥**で、テストホストが `Sophia.app` そのものだったため
> **同一プロセス内でエンジンが2つ動き、同じモデルを2回読んでいた**（比がぴったり2.000）。
> **観測しようとして観測対象を2倍にしていた**という失敗である。
> 詳細と修正は [docs/BENCH_RESULTS.md](docs/BENCH_RESULTS.md)。

**そして問題は未解明のまま残っている。** 最初の観測 ── GUI アプリ**単体**で2往復し、
TTFT が **0.97秒 → 11.87秒** になった件 ── はプローブが存在しない状態のものである。
**「4.6GB しか使っていないアプリが、2往復目に11.87秒かかった」**という、
より説明の難しい形で問いが残った。

**この数字を信用しすぎないこと。** Debug ビルド（デバッガは非接続）
（[docs/MLX_SWIFT.md](docs/MLX_SWIFT.md) 落とし穴15 は計測時にデバッガを外せと書いている）・
思考モードON・自己認識ON・起動時点でスワップ4GB使用済み、という条件での2点である。
取り方は「[使い方](#使い方)」の `make app-stats`。

> **TTFT 0.97秒 に対し TTFR 7.71秒**（1往復目）── 「何かが出る」までは1秒でも、
> **利用者が読みたい本文が出るまでは約8秒**かかっている。思考モードONの代償がここに出る。

**ファンレスのため、連続使用で速度が約半分に落ちる。** これは Ollama 側の実測で確認済みで、
設計上の前提として扱っている（詳細は [docs/DESIGN.md](docs/DESIGN.md) 第2章）。
熱はランタイムではなく筐体の性質なのでアプリでも同じことが起きるはずだが、
**アプリ側は2往復しか取っていないため連続使用時の落ち込みを確認できていない。**

## 使い方

### アプリ（フェーズA1）

```bash
make app-setup       # 初回のみ: Metal ツールチェーン導入（約688MB）
make app-run         # ビルドして起動（Debug）
make app-test        # 永続化層の単体テスト（GPU・モデル不使用）
make test-inference  # 思考タグ分離（FR-17）の単体テスト。推論は走らない
```

初回起動時にモデル（`mlx-community/Qwen3-8B-4bit` / **約4.6GB**）の取得が必要。
落ちてくるのは重みとトークナイザの9ファイルだけで、**LICENSE も README も含まれない**（実測で確認）。
モデル自体は apache-2.0 だが、A4 で同梱配布するならライセンス文と帰属表示は自分で入れる必要がある
── [docs/MODELS.md](docs/MODELS.md)。

#### 速度を測る

```bash
make app-stats   # 実測ログ付きで起動（[STATS] を logs/mlx-stats.log へ）
make stats-tail  # そのログを別窓で追尾
```

`make app-run`（= `open`）では **[STATS] 行が1バイトも残らない。** `open` は LaunchServices 経由で
fd 0/1/2 がすべて /dev/null に繋がるためで、`log stream` でも拾えない（生の `write(2)` のため）。
`make app-stats` は `open --stderr` で fd 2 をログファイルへ付け替えている。
**この経路で取れているのは連続2往復ぶんだけ**（上記「実測されている性能」を参照）。

> **起動中のアプリがあると `open` は新しいビルドを起動しない。**
> 修正したはずの不具合が直っていないように見えたら、まずこれを疑うこと。
> 計測・確認の前に `pkill -f Sophia.app` してから起動する。

### 開発用バックエンド（Ollama + Open WebUI）

```bash
make up        # Ollama と Open WebUI を起動
make status    # 稼働状況といまメモリに載っているモデル
make down      # 停止
```

起動後 `http://localhost:8081` をブラウザで開く。Open WebUI は**モデルの振る舞いを見比べるための
参照UI**であって、Sophia アプリのフロントエンドではない。**アプリのモデル（MLX）はここに載らない。**

**アプリ（MLX）と Ollama は同じメモリを取り合うため、16GB機では同時に使わないこと。**
両方が載っている状態で測ると数字が壊れる。

性能を変えたいときは [docs/TUNING.md](docs/TUNING.md) でつまみを1つ選び、
`.env` か `modelfiles/*.Modelfile` を編集して `make restart` または `make models`。
効果は `make bench-save NOTE="変えた内容"` で数字として残す。
ただし TUNING のつまみと `make bench` は**この Ollama スタック向け**であり、
アプリ側にそのまま効くものは多くない。

> **Modelfile は編集しただけでは反映されない。`make models` が必要。**
> そのうえで、**`make models` はアプリには何も反映しない**（別系統。上述）。

## 前提と制約

- **開発機**: MacBook Air M3 / 16GB / ファンレス。**これは制約ではなく手段である**（[docs/VISION.md](docs/VISION.md)）
- モデルに回せる実質枠は **約9〜10GB**。7〜8Bが常用の最適解、14Bが上限
- アプリ単体の常駐は **約5.4GB の見積り**（重み4.6 + KV約0.7 + シェル約0.05）に対し、
  **実測ピークは 4,615 → 4,656MB**（短い2往復のみ。長い文脈で KV が伸びた状態は未計測）
- 長時間の連続生成では熱制限で性能が落ちる
- Open WebUI は **8081** で待ち受ける（既定の8080は開発機上の別プロジェクトと衝突するため）。
  `.env` の `WEBUI_PORT` で変更できる

制約の詳細と対処は [docs/TUNING.md](docs/TUNING.md) 第0章（Ollama スタック前提）と
[docs/MLX_SWIFT.md](docs/MLX_SWIFT.md) 第8章（アプリのメモリ見積り）。
