### 検証で判明したこと

#### 発見1: 思考モードがトークン予算の9割を消費する

`qwen3:8b` は応答前に思考テキストを出力する。同一プロンプトでの比較:

| 条件 | 思考 | 本文 | 消費トークン |
|---|--:|--:|--:|
| 思考モード有効（既定） | 1,075文字 | 112文字 | 300（上限到達） |
| 思考モード無効 | 0文字 | 56文字 | 32 |

TTFT 15〜19秒の正体はこれ。生成上限が小さいと**本文に到達しないまま打ち切られる**
（ベンチのcodeプリセットで実際に発生し、TTFTがnanになった）。

※ 上段は1,187文字を300トークンで出した計算になり、日本語の校正値（1文字≒0.5トークン）と
合わない。思考が英語だった可能性があるが記録が無く未確認（DESIGN 2.1 に未解決として記載）。

→ 設計へ反映: 思考を折りたたみ領域に分けて表示し、無言の待機を作らない（FR-17/18、DESIGN 第6章）。

#### 発見2: ファンレスの熱制限で速度が約半分になる

実行順を入れ替えて再計測した結果:

| 実行順 | sophia-coder | sophia-chat |
|---|--:|--:|
| chat先行 | 9.0 tok/s（2番目） | 13.4 tok/s（1番目） |
| coder先行 | 14.1 tok/s（1番目） | 7.0 tok/s（2番目） |

**先に走った方が速い。** モデルの性能差ではない。`sophia-chat` のTTFTも
冷間15.4秒に対し高温時28.9秒へ悪化した。

→ 設計へ反映: 連続使用時の実力値を **7〜9 tok/s** とし、NFR-03b の基準とした。
当初 NFR-03 に置いた「10 tok/s以上」は連続負荷下では**未達**であるため、
冷間13 tok/s以上・連続7 tok/s以上へ改めた。

### 判断と理由

- **Open WebUI を Docker ではなく uv で入れた**
  16GB機で Docker Desktop を常駐させると VM だけで数GB消費し、モデルに回せるメモリが減るため。
  開発機の従来方針では MySQL 等は Docker を使うが、常駐コストが直接性能に効く本件では例外とした。

- **Open WebUI のポートを 8081 にした**
  既定の 8080 は同一マシン上の別プロジェクトが使用中だった。
  開発機のポート台帳を事前に確認して検知した。

- **常駐サービス（brew services）ではなくスクリプト起動にした**
  チューニングのたびに再起動が要るため、設定が `.env` に見える形で置かれ、
  明示的に再起動できる方が扱いやすい。

- **Flash Attention と KVキャッシュ量子化(q8_0)を既定で有効にした**
  長いコンテキストのメモリをほぼ半減できる一方、品質劣化は小さい。
  16GBという制約下では最もコスパが良い。Homebrew の caveats も同じ組み合わせを提示している。
  → **この判断根拠は 2026-08-16 の実測で否定された**（削減は常駐比8%であって半減ではなく、
  速度も f16 の方が約6%速い）。結論として q8_0 は据え置いたが理由は別
  （ページング回避）。同日の「判断と理由」および TUNING 第5章を参照。

- **`OLLAMA_MAX_LOADED_MODELS=1` にした**
  既定のままだとチャット用とコード用が同時にメモリに載り、スワップして両方遅くなるため。

- **ベースモデルを Qwen 系のままとし、国産モデルへは切り替えなかった**
  (1) 日本語モデルの多くは Llama/Qwen への追加学習で、土台の性能に依存する
  (2) コード特化の国産モデルがほぼ無く、用途の半分が弱くなる
  (3) **Qwen3-8B / Qwen2.5-Coder-7B は Apache 2.0 で再配布・商用利用が可能**であり、
  単体配布アプリという要件と噛み合う。
  なお「国産AI」という表現は、モデルが国産でない以上、事実と食い違うため採用しない。

- **推論エンジンを抽象化する方針を先に決めた**（DESIGN 第4章）
  開発は Ollama、配布は同梱ランタイムと実行方法が変わるため。
  後から差し替えると UI ごと作り直しになる。

- **文書を再構成した**
  当初の `APP_PLAN.md` を廃止し、
  `REQUIREMENTS.md`（要件定義）/ `DESIGN.md`（設計）/ `ROADMAP.md`（行程）へ分割。
  要件と設計と計画が1ファイルに混在していると、変更時にどこを直すべきか判断できないため。

## 2026-08-16 入力処理（プリフィル）が遅い問題の切り分け

### 目的

Open WebUI 経由の応答が遅い。入力処理速度がベンチでは 3,610 tok/s、
実環境では 140 tok/s と**25倍食い違う**。この差の正体を突き止める。

当初の主要な仮説は「`OLLAMA_KV_CACHE_TYPE=q8_0` が Metal で入力処理を遅くしている」だった。

### 結論（先に）

**仮説はすべて否定され、前提そのものが誤っていた。**
25倍の食い違いは実在せず、**3,610 tok/s の側が偽値**だった。
真の原因は設定ではなく、**Open WebUI が「こんにちは」の一言に4,786トークン送っていたこと**。

### 検証で判明したこと

#### 発見3: 「25倍の差」は存在しない。ベンチ側が偽値だった

`scripts/bench.py` は同一プロンプトをウォームアップ＋計測回で繰り返すため、
2回目以降はプレフィックスキャッシュにほぼ全命中する。
実計算はほぼゼロなのに `prompt_eval_count` は全トークンを数えるため、
割り算した tok/s だけが何十倍にも膨らんでいた（Ollama の既知の挙動）。

物理的にありえないことは算術で確認できる。
2 × 8.19e9 params × 3,610 tok/s = **59 TFLOP/s**。
M3（8コアGPU）の FP16 理論ピークは約6.6 TFLOP/s で、**9倍超過**している。

プロンプト先頭に nonce を入れてキャッシュ命中を壊して測り直した真値は **114〜167 tok/s**
（理論ピークの33〜41%で妥当）。**実環境で見えていた140 tok/s は異常値ではなく、素の実力値。**

→ 「遅い原因を探す」ではなく「そもそも遅くない。長すぎるだけ」という問題に変わった。

#### 発見4: 4,786トークンの95%は Open WebUI が自動注入していた

素の Ollama API へ「こんにちは」を送ると245トークン。
Open WebUI 0.11.0 経由だと4,786トークン。**差の約4,550トークンはクライアント由来。**

正体は native function calling 用の**ビルトインツール群のJSONスキーマ**であり、
システムプロンプトでもRAGでもなかった
（`utils/middleware.py:2643-2649` で `use_builtin_tools` が立ち、
`utils/payload.py:321-322` で Ollama のペイロードへコピーされる）。
なおツールの個数は当初32個と数えたが、カテゴリ別の内訳を足すと35個になり整合していない。
内訳のトークン数も合計が実測を約456トークン超過している（TUNING 第2章の注記を参照）。

→ 入力処理は正常に約140 tok/s で動いており、**4,786トークンで32〜35秒かかるのが正しい挙動**。

#### 発見5: `.env` に書いた設定の半分は「効かない」か「見当違い」だった

- **効かない**: Open WebUI は設定をDBに保存し、環境変数は
  「DBにまだ行が無いキー」にしか適用されない（`models/config.py:256`）。
  初回起動後に `.env` を書き換えても黙って無視される。
  `.env` 冒頭の「編集して `make restart` すれば反映される」が**成立していなかった**。
- **見当違い**: 既存の `ENABLE_*_GENERATION` 群は裏のLLM呼び出し回数を減らすが、
  **1回あたりのプロンプト長は1トークンも減らさない**。
  `ENABLE_WEB_SEARCH=False` に至っては既定が既に False で削減量ゼロ。
  「既定で有効だとプロンプトにツール定義が注入される」というコメントは誤りだった。

#### 発見6: 「512トークンごとにKVを捨てて再計算」も誤読だった

`cached n_tokens` は512ずつ**増えて**おり、チャンク処理の記帳にすぎない。
決定的な証拠は実計算トークン数で、**4,560 = 4,793（全体） − 233（キャッシュ命中）** が
ぴったり一致する。捨てて再計算していればこの数は数倍に膨らむ。

#### 発見7: この機体ではメモリ逼迫が熱より大きい雑音源

計測中の空きメモリ1.3〜2.8GB、スワップ使用6〜7GB/8GB。
**同一条件・4,786トークン16件で31.7〜154.5秒（4.9倍の開き）。**
1回の計測中にページアウト90,104ページ（約1.4GB）が起きたブロックは、全長で速度が半分になった。

**条件間の差（KV型で6%）より同一条件内のばらつきの方が大きい。**
この状態では設定のA/Bをやっても判定できない。実際 `num_batch` 512 vs 1024 は判定不能に終わった。

### 判断と理由

- **`OLLAMA_KV_CACHE_TYPE` は `q8_0` のまま据え置いた**
  計測は f16 が約6%速いことを示した（3ラウンドとも f16 が速い）が、
  常駐メモリは f16 6.5〜6.6GB / q8_0 6.0〜6.1GB で**0.5GBの差**がある。
  スワップ6〜7GB使用の逼迫下ではページングが最大4.9倍の劣化を生んでおり、
  **6%の速度差より0.5GBの確保を優先**した。
  ただし「速度で有利だから q8_0」ではないので、TUNING.md の
  「効果：大 / コスパ最良」「メモリをほぼ半減」という記述は誤りとして全面的に書き換えた
  （実際の削減は常駐比8%であって半減ではない）。
  メモリに余裕がある使い方をするなら f16 の方が速い、と併記した。

- **`ENABLE_PERSISTENT_CONFIG=False` を追加した**
  これを入れないと `.env` の Open WebUI 側設定が今後一切反映されない（発見5）。
  「`.env` を編集して `make restart` すれば反映される」という本プロジェクトの前提を
  実際に成立させるための措置。副作用として管理画面での設定変更が再起動で消えるが、
  1人利用であり、設定の権威が2箇所にある方が事故を生むため許容した。

- **`ENABLE_MEMORIES` / `ENABLE_CALENDAR` / `ENABLE_AUTOMATIONS` / `ENABLE_NOTES` を追加した**
  ツール定義そのものを減らす唯一の環境変数群で、合計約3,080トークン削減。
  逆に既存の9個は1つも削除しなかった。**全て実在する正しい名前だった**ため
  （インストール済みパッケージの `config.py` で17個すべて確認済み）。
  ただし効果を誤解させるコメントは全て書き直した。

- **環境変数だけでは足りないことを明記した**
  knowledge / time / chats / tasks の約1,700トークンには対応する環境変数が存在せず
  （`ENABLE_KNOWLEDGE` などは実在しない）、モデルの capability
  「Builtin Tools」を off にするしかない。
  **環境変数だけの到達点は約1,600トークン＝プリフィル約10秒**で、目標にぎりぎり届かない。

- **`bench.py` の入力処理列を「無効」として BENCH_RESULTS.md に明記した**
  数値を消すのではなく、無効である旨と理由を残した。
  過去の記録を削ると「なぜ3,610という数字が出回っていたか」が追えなくなるため。

- **2026-08-16 13:00 の計測節に「⚠ 無効」を付けた**
  `num_batch` を固定しておらず q8_0=512 / f16=1024 で走っていたため、
  KV型の比較として成立していない。自分の計測でも同じ罠を踏みうるので、
  削除せず失敗例として残した。

#### 発見13: 計測値のうち、どれが実測でどれが概算か

> 対処は文字数からの概算をやめてトークナイザで数えること。

#### 発見15: `@State` を含む Swift コードでアプリが確実に固まる

**シンタックスハイライタ（`SyntaxHighlighter`）の識別子ブランチが無限ループしていた。**

`isIdentifierStart` は `#` と `@` を識別子の先頭として受け付けるのに、
`isIdentifierPart` はどちらも含まない。結果、識別子として走査を始めたのに
`while` が**1文字も進まないまま `i = end`（= `i`）で戻り、同じ位置を永久に読み続ける。**

**`@` か `#` が来た時点で走査器が停止する。**
つまり **`@State` や `@MainActor` を含む Swift コードを1つでも表示すると必ず固まる。**
SwiftUI のコードを生成させたら確実に踏む経路だった。
Python やシェルが無事だったのは、`#` が行コメントとして**先に**処理されていたからにすぎない。

修正は「先頭の1文字を必ず取り込む」＝ `end = i + 1` から始めるだけ。これで前進が保証される。
`SyntaxHighlighterTests` 7件を追加した。**ハングしたときにテストごと止まらないよう、
時間切れで落とす形にしてある**（無限ループの回帰は「失敗」ではなく「終わらない」形で現れるため）。

> **教訓: 文字集合を2つの述語に分けたら、両者の非対称が即ループになる。**
> 「開始として認めた文字が、継続としても認められるか」を必ず確認すること。

入力長そのもの / **モデルの都度ロード**。

**【未確認】** 残る候補は ①待機中のページアウト（本命）②KV持ち越し無しの再プリフィル

> **アプリの性質ではなく「そのときの機体の状態」を測った可能性が相当ある。**

#### 発見17: `RSS` は MLX の重みを数えない（自分の推論の撤回）

**同日、退避を確かめようとして RSS を根拠にしたが、これは無効だった。**

アプリを起動して**無操作のまま**測った減衰:

| 経過 | RSS | phys_footprint |
|--:|--:|--:|
| **30秒** | **479 MB** | **4,534 MB** |
| 7分 | 97 MB | 4,534 MB |
| 14.5分 | 68 MB | 4,535 MB |

**モデルを読み込んだ直後（退避のしようがない時点）で、既に RSS には載っていない。**
重みは `IOAccelerator (graphics)` の確保分（4,396MB Dirty）で、**RSS はこれを数えない。**

**残った証拠は compressor の増減の対称性**（起動で +5.08GB / 終了で −4.80GB）。
アプリのメモリが compressor に載っていること自体は、これで裏が取れる。

**だが決定的な問いが残った。** 空きページは 6,982（約109MB）しかない。
**アイドルしたから退避されたのか、そもそも空きが無くて確保時点から圧縮されているのか**を
この観測は区別できていない。**対処がまったく違う**（前者は wired、後者はモデルを小さくする）。

> **教訓: 指標が対象を測っているかを、先に確かめること。**
> `peak_mb` が residency を測らないことは見抜いたのに、
> **その代わりに持ってきた RSS も測っていなかった。** 同じ誤りを別の指標で繰り返した。

#### 発見18: 生成中のワーキングセットが約9GB。**ただし計測は交絡により無効**

**アプリが生成中に必要とするのは約9GB**（`IOAccelerator (graphics)` 8,952MB）。モデルは4.6GB。
**余分な約4.4GBの正体は未解明で、これが最優先の調査対象。**

**制御実験を行ったが、無効だった。** 計測用のテストホストと並行して、
**利用者がデスクトップアプリを開いていた** ─ 9GB × 2 で **16GB機に18GBを要求**していた。
同一入力でプリフィルが 0.99秒〜56.71秒 まで振れ、崩れた往復では系全体で20GB規模の
