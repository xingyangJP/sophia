## 到達点

> **新しいアプローチによって、現在の約1/1000のエネルギーで同じ仕事をするAIを完成させる。**

デスクトップアプリ（トラックA）も独自モデル（トラックB）も、この目標に対する
**通過点**であって終点ではない。

## 問題の所在

現在のAIは、問いの難易度に関わらず同じ計算量を払う。
「こんにちは」の5文字にも、複雑な設計相談にも、**全パラメータを起動する**。
手を抜く仕組みが存在しない。

### 本プロジェクトでの実測（2026-08-16）

M3 MacBook Air / 16GB で `sophia-chat`（qwen3:8b, 8.19B params）に
「こんにちは」と送ったときの実測値。

| 項目 | 実測 |
|---|--:|
| 入力トークン | 1,911 |
| 入力処理 | 12.9 秒（148 tok/s） |
| 生成 | 17.8 秒（231トークン / 13 tok/s） |
| **合計** | **30.7 秒** |
| 演算量 | 約 2.3 TFLOP/s を持続 |

**5文字の挨拶に30秒。** これが今日のAIの実態であり、出発点である。

## 1/1000 をどう分解するか

現時点での見立て。**すべて未検証の仮説であり、確度は低い。**
実測で潰しながら書き換えていく。

### 第1因子: そもそも無駄を送らない（10〜20倍 / **既に実証済み**）

この30秒のうち、**入力1,911トークンの大半は誰も必要としていないツール定義**だった。
対策前は4,786トークンあり、95%がクライアントの自動注入。

| 状態 | 入力トークン | プリフィル |
|---|--:|--:|
| 対策前 | 4,786 | 34 秒 |
| 環境変数のみ | 1,911 | 12.9 秒 |
| ツール注入を全停止（見込み） | 約231 | 約1.5 秒 |

**アーキテクチャを1行も変えずに20倍。** エネルギー問題はモデルの前に、
ソフトウェアの無駄から始まっている。ここは既に手が届いている。

### 第2因子: 難易度に応じてモデルを選ぶ（10〜30倍 / 実装可能）

「こんにちは」に8Bは要らない。0.5B で十分。
問いの難易度を判定して適切な規模へ振り分ける（ルーティング／カスケード）。
平均消費を大きく下げられるが、**判定自体のコスト**と誤判定時の品質低下が課題。

### 第3因子: 全部を起動しない（10〜50倍 / 研究段階〜実用）

- **疎な活性化（MoE）** — 一部の専門家だけを起動する。既に実用化されている
- **早期終了** — 確信が持てたら途中の層で打ち切る
- **極端な量子化** — 1bit / 三値化。行列積を使わない構成の研究もある

### 第4因子: アーキテクチャそのものを変える（未知）

- 状態空間モデル等、注意機構の二乗コストを持たない構成
- アナログ計算・インメモリ計算・ニューロモーフィック（**ハードウェア側**）

### 掛け算として

20 × 20 × 10 = 4,000。**算術的には 1/1000 は射程内**に見える。
ただし各因子は独立ではなく、掛け合わせるほど品質を保つのが難しくなる。
**「1つの巨大なモデルが全てに答える」という前提を捨てること**が共通する条件になる。

## ⚠ 現行ロードマップとの矛盾

**この目標に照らすと、ROADMAP のトラックB（M1マージ → M2 LoRA → M5継続事前学習）は
エネルギー効率に一切寄与しない。**

| 手法 | 振る舞い | **計算量** |
|---|---|---|
| モデルマージ | 変わる | **変わらない** |
| LoRA / fuse | 変わる | **変わらない** |
| 継続事前学習 | 変わる | **変わらない**（むしろ規模を上げがち） |

これらは「自分だけのモデル」は作れるが、「1/1000のモデル」は作れない。
**目標が2つあり、手段が片方にしか向いていない。**

### 整理

| 目標 | 有効な手段 |
|---|---|
| 自分だけのモデルにする | マージ / LoRA / 継続事前学習 |
| **1/1000のエネルギーにする** | **無駄の除去 / ルーティング / 疎な活性化 / 蒸留 / 新アーキテクチャ** |

両立させるなら、**「自分の用途に絞った小さなモデルへ蒸留する」**が交点になりうる。
汎用性を捨てて用途を絞れば、規模を落としても品質を保てる可能性がある。
ROADMAP の見直しが必要。

### 訂正: LoRA には省エネの道がある（2026-08-16 追記）

上の「LoRAは計算量を変えない」は**不完全だった**。
1トークンあたりのコストは確かに変わらない。しかし
**「毎回説明しなければならないトークン」を消せる。**

パーソナライズを文脈に注入する方式では、毎ターン数百トークンを払い続ける。

| 方式 | 毎ターンのコスト | 1,000ターンの累計 |
|---|--:|--:|
| 文脈に注入（500トークン） | 3.4 秒 | **約57分** |
| 重みに焼き込む（LoRA） | **0** | **0** |

**一度払って、二度と払わない。** これはトラックBがエネルギー目標に貢献する正当な道である。

## 開発機を強化しない（原則）

**MacBook Air M3 / 16GB / ファンレスという非力な環境は、制約ではなく手段である。**

強い機体は無駄を隠す。実際、4,786トークンの無駄な注入は、この機体で
**34秒という痛み**として現れたから発見できた。潤沢なメモリと帯域があれば
一瞬で終わり、誰も気づかないまま残り続けていた。

**この機体は非効率を可視化する測定器である。**

| | |
|---|---|
| 強い機体で最適化すると | 2倍の改善と100倍の改善が、どちらも「一瞬で終わった」に見える |
| 弱い機体で最適化すると | 差が秒単位の体感として現れ、追う動機が生まれる |
| 移植性 | M3/16GBで快適なものはどこでも動く。**逆は成立しない** |

したがって、**開発機の買い替え・メモリ増設は原則として行わない。**
1/1000を目指す上で、効率の悪さが見えない環境で作業することが最大のリスクになる。

### この原則のコスト（承知の上で受け入れる）

- **計測が汚れる。** スワップ6〜7GBの逼迫により、同一条件の計測が
  31.7〜154.5秒（4.9倍）にばらついた。信号と同時に雑音も増える
  → 対策: 冷却待ちと反復、中央値の採用（`scripts/bench-prompt.py`）
- **学習はできない。** 推論効率の研究には最適だが、M4以降の学習は
  クラウドが必要。ROADMAP 第4章の移行計画がこの部分を担う

**役割分担: 推論効率の研究はこの機体、学習はクラウド。**

# 方法論

ここから先は「1/1000をどう探すか」の設計思想。因子分解より上位に置く。

## 中核となる操作: 要約

**曖昧で長いものを、確定して短いものに変える。** これが本プロジェクトの中核操作である。

一見別々に見える課題が、すべて同じ操作に収束する。

| 場面 | 実体 |
|---|---|
| 文脈の圧縮 | 過去の会話の要約 |
| メモリ | 事実の要約（何を覚えておくべきか） |
| 意図の確定 | 依頼の要約（曖昧な指示 → 確定した仕様） |
| 決定論的処理への引き渡し | 要約が完了した状態 |

### なぜ効くか: 要約は投資である

コストは一度きり、節約は毎ターン。会話が長いほど回収が増える。

| | コスト |
|---|--:|
| 5,000トークンを200トークンへ要約 | 34 秒（一度） |
| 要約せず20ターン継続 | 34 × 20 = **680 秒** |
| 要約して20ターン継続 | 34 + (1.4 × 20) = **62 秒** |

**投資34秒、回収618秒。約11倍。**
さらに要約は生成より易しい仕事なので、**小さいモデルに一度払って、
大きいモデルの毎回を節約する**構成が取れる。層の分割とも噛み合う。

### 知能の側から見ると

要約とは「何が重要かを判断し、残りを捨てる」ことである。
**それは理解そのものと区別がつかない。** 完璧に要約できることは、完全に理解したことに等しい。

したがって「要約を中核に据える」は単なる最適化技法ではなく、**アーキテクチャの主張**である。

### 難所と、その支え

**捨てたものが後で必要になったとき**に破綻する。対処は2つ。

1. **原ログを完全な形で保持し、必要なら戻れるようにする**
2. 何を捨てるかの判断精度を上げる（本質的に難しい部分）

**1があるから2で失敗しても致命傷にならない。**

そして原ログは安い。実用的な使用量で **年間およそ18MB**（1日50通 × 1,000字）。
ここに圧縮アルゴリズムを工夫する価値は無い ─ 解くべき問題が存在しない。

> **完全なログを安く持てることが、大胆に要約する自由を支える。**
> 保存は可逆・完全に、文脈は不可逆・意味だけに。求めるものが正反対である点に注意。

## パーソナライズ

要約の質は、その人を知っているかで決まる。
「この人がこう言ったら、こういう意味だ」を読めなければ、捨てるべきものを誤る。

### モデルに備わっているか

| | 備わっているか |
|---|---|
| 行間を読む能力そのもの | **ある。** LLMが最も得意とする部分 |
| **その人固有の**行間を読む能力 | **無い。** セッションをまたいで何も覚えていない |

**能力はある。データが無い。** これが正確な状態である。

### データは使うだけで貯まる

2026-08-16 のセッションで、アシスタントは5回訂正された。
各訂正がそのままパーソナライズの教師データになる。

| 発言 | 誤読 | 実際の意味 |
|---|---|---|
| 「自分だけのAI」 | RAGのことか | 新しいモデルを作ること |
| 「圧縮」 | ファイル圧縮 | **要約** |
| 非力なマシン | 買い替えを提案 | 制約こそが手段 |
| ENV.md | 指示通り更新 | 触らない（方針が変わった） |
| 「自分で作った〜」 | 良い案 | 読み手が混乱する一人称 |

**訂正の一つ一つが、その人固有の行間の定義である。**
これが「まず作って使う」を優先する理由でもある ─ データは使わないと集まらない。

### 内容と様式を分けて記録する

人は変わる。しかし変わり方が一様ではない。

| | 例 | 更新方針 |
|---|---|---|
| **内容** | 知識、技術スタック、いまのプロジェクト、意見 | **陳腐化する。** 上書き・期限が要る |
| **様式** | 説明の粒度、断定への態度、訂正のされ方、判断の速さ、何に苛立つか | **蓄積する。** 強化されていく |

**様式は「何を話したか」ではなく「どう話したか」に現れる。**
同じ記憶領域に混ぜると、陳腐化した内容が様式まで汚す。**分けて持つこと。**

### 初期化: 質問で事前分布を作る（コールドスタート対策）

行動ログによるパーソナライズには冷間開始問題がある。データが貯まるまでの数週間、
誤読だらけの体験を利用者に強いることになる。

**対策（2026-08-16 発案）: 初回に、必要な数だけ質問に答えてもらう。**
人間同士が阿吽の呼吸に至るには長い時間がかかる。そのショートカットとしての、
洗練された質問群である。

> **要件と設計に落とした（2026-08-17）。**
> [REQUIREMENTS.md](REQUIREMENTS.md) **FR-24〜29 / NFR-11・12 / 未決事項 6〜8**、
> 設計は [DESIGN.md](DESIGN.md) **第14章**。
> **本節の原則が正であり、DESIGN 第14章はそれを実装できる粒度に落としたものである。**
> 食い違いを見つけたら本節を正とすること。

#### 設計原則

| 原則 | 理由 |
|---|---|
| **様式を聞く。内容を聞かない** | 内容は陳腐化する。様式は安定する（内容/様式の分離と同じ根拠） |
| **自己申告でなく、二択の実例で聞く** | 人は自分の好みを正確に申告できない（宣言選好と顕示選好の乖離）。「簡潔が好きですか」ではなく、同じ内容の回答例AとBを見せて選ばせる。ペア比較は絶対評価より信頼できる |
| **情報利得の大きい順に、適応的に** | 前の答えが次の質問を決める。利得が閾値を下回ったら打ち切る。「必要な数だけ」の実装 |
| **全部を最初に聞かない** | 抽象的な事前質問より、実際の分岐が起きた瞬間の文脈内質問の方が信号が強い。初回は3〜5問に絞り、残りは使用中に集める |

#### 限界を先に認める

**暗黙知は質問では取れない。** 本人が言語化できないものは、どう聞いても出てこない。
実際、2026-08-16 の5つの誤読（「圧縮」=要約 等）のうち、事前の質問で防げたものは
おそらく無い。本人も聞かれるまで「圧縮と言ったら要約を指す」とは言語化していない。

質問がショートカットするのは**言語化できる半分**だけ。残り半分（暗黙知）は
観察＝ログでしか得られない。両方が要る。質問の役割は、
ログが貯まるまでの期間を快適にすることである。

#### GAとの接続 ─ 競合せず、噛み合う

| | 役割 |
|---|---|
| 質問の答え | **初期個体（事前分布）。** ランダム初期化より収束が速い |
| 行動ログ | **適応度関数。** 質問で得た仮説を、実際の訂正回数で検証・淘汰する |

さらに**質問自体も測定対象になる**。「どの質問の答えが後の訂正を予測できたか」は
ログから取れるため、質問セットそのものを淘汰できる。
洗練された質問は設計するものではなく、進化させるものである。

#### 副次的な利点

質問由来の規則は**最初から言語化されており、見せられる・編集できる**。
「焼き込まれた思い込みは外から見えない」というリスク（下記）への対策を、
初期化の時点で満たしている。

### 人の識別

**ログイン機能は不要。** Electron の `app.getPath('userData')` は
macOS のユーザーアカウントごとに分かれるため、
**「人 = OSユーザーアカウント」がコードを書かずに手に入る。**
共用機での家族の分離も自動的に成立する。

未決の論点: **同一人物が2台目の端末を持ったとき。**
同期させると会話が端末外に出て NFR-01 と衝突する。
手動エクスポート／ローカルネットワーク内同期／同期しない、のいずれか。いま決めなくてよい。

### リスク

**焼き込まれた思い込みは、外から見えない。**

上の5回の誤読は、少なくとも「何を誤読したか」が会話の中で見えていた。
重みや記憶に固定された解釈は見えないまま外し続ける可能性がある。
**「なぜそう解釈したか」を提示できること**、または**訂正が確実に効くこと**が設計要件になる。

## 探索方法: 遺伝的アルゴリズム

「何がコアか」は事前に決められない。**決めなくてよい。淘汰に決めさせる。**

| 手法 | コアの決め方 | 評価 |
|---|---|---|
| 要約の連鎖 | 要約されるたびに言及されたものが残る | 基準が曖昧。**ドリフトする** |
| **遺伝的アルゴリズム** | **適応度で測り、生き残ったものが残る** | 基準が明示的で検証可能 |

### 当てはめ

| GAの要素 | Sophia での中身 |
|---|---|
| 個体 | パーソナライズ設定（規則・記憶の集合・システムプロンプト） |
| **適応度** | **訂正された回数の少なさ。** ログから機械的に取れる |
| 選択 | 訂正が少なかった設定を残す |
| 交叉 | 2つの設定を混ぜる |
| 突然変異 | 規則を足す・消す・書き換える |

### なぜ勾配法でなくGAか

**探索対象が離散で微分できないから。**

「どの記憶を残すか」「いつ思考モードを使うか」「どの規模のモデルに回すか」は
どれも離散的な判断であり、勾配が定義できない。ここがGAの領分である。

| | 対象 | 手法 |
|---|---|---|
| **遺伝的アルゴリズム** | 規則・記憶の取捨・判断ポリシー・プロンプト | 離散・微分不可 |
| **LoRA** | 重み | 連続・微分可能。勾配法が圧倒的に効率的 |

**両方要る。棲み分けるべきもので、競合しない。**

### 適応度に消費エネルギーを入れる

進化させる対象をパーソナライズに留めず、**判断ポリシー**まで広げる。

- いつ思考モードを使うか（実測で約10倍の差）
- どの規模のモデルに回すか
- 文脈をどこまで要約するか

適応度を **「品質 ÷ 消費エネルギー」** と定義すれば、
**1/1000 という目標がそのまま最適化対象になる。**

### 最大の問題: サンプル効率

GAは多数の評価を要するが、ここでの1回の評価は「人間との実際の会話」である。
利用者に数千回付き合わせることはできない。

**解決策: 過去ログでのオフライン・リプレイ評価。**
候補設定を記録済みの会話に対して評価する ─ 「この設定なら、あの訂正を予測できたか」。
人間を待たずに世代を回せる。

**これも原ログを完全に保持していることが前提**になる。年間18MBの保存が、
要約の安全網であると同時に、進化の評価基盤でもある。

## 当面の指針

1. **測ることを続ける。** 「1/1000」は主張ではなく測定対象である。
   `docs/BENCH_RESULTS.md` に積み上げた実測が唯一の判断材料になる
2. **無駄の除去を先にやり切る。** 第1因子は既に20倍が見えており、
   アーキテクチャ研究より確実で安い
3. **アプリ開発（トラックA）は止めない。** 自分の実利用こそが
   「何が本当に必要な計算か」を教えてくれる。使わない機能に払っている
   コストは、使ってみるまで分からない

## 未検証・未決定

- 1/1000 の分解は**すべて仮説**。各因子の実現可能性を検証していない
- どの因子から着手するかの優先順位が未決定
- 「同じ仕事」の定義が未定。何をもって品質が保たれたと判断するのか。
  **品質評価基盤が無いままでは、効率化と劣化の区別がつかない**（ROADMAP 第3章）
