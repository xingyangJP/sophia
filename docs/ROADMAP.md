## 基本方針

**ローカルは終点ではなく出発点。** 0円で回せる範囲で性能を上げ続け、
**ローカルの天井に当たった時点でクラウドへ移行する。**

移行は「いつか考えること」ではなく、**あらかじめ条件を決めておく判断**として扱う。
条件は第4章に定義する。

### 2本のトラック

| トラック | 内容 | 依存関係 |
|---|---|---|
| **A: アプリ（器）** | **macOSネイティブアプリ（SwiftUI + MLX Swift）** | モデルの完成を待たない |
| **B: モデル（中身）** | 独自モデルの開発 | アプリの完成を待たない |

**両者は独立して進む。** 接点は「**MLX形式（safetensors）のディレクトリ1つ**」だけで、
アプリはそれを読むだけの構造にしてある（[DESIGN.md](DESIGN.md) 第7章 経路C）。
どちらかが止まっても、もう一方は進められる。

> **接点の形式が GGUF から MLX形式へ変わった。**（2026-08-16 / [DESIGN.md](DESIGN.md) 第10章、リスク14）
> 推論を MLX に移した以上、学習側の出力も MLX形式で出すのが自然になった。
> **「接点はファイル1つ、両トラックは待ち合わせない」という構造自体は変わっていない。**
> 既存の GGUF 資産（`modelfiles/` の成果）はアプリへは載らないが、
> Ollama 側は計測・比較の基盤として残す。

### クラウド移行後も変わらないこと

**推論と配布はローカルのまま。クラウドを使うのは学習だけ。**

```
[クラウド]  学習・微調整  ──→ 完成した重み(MLX形式) ──→ [ローカル] 推論・配布
```

学習をクラウドへ移しても、**利用者のデータが外部に出ることはない**。
アプリの価値（NFR-01）はこの分離によって維持される。
つまりクラウド移行は、アプリの設計にもプライバシー要件にも影響しない。

### エネルギー目標との関係（VISION との交点）

**上の段階設計は「自分だけのモデル」だけを見ている。**
[VISION.md](VISION.md) が置いた最終目標「現在の約1/1000のエネルギーで同じ仕事をするAI」に対し、
M1マージ / M2 LoRA / M5継続事前学習は**1トークンあたりの計算量を1ミリも変えない**
（[VISION.md](VISION.md)「現行ロードマップとの矛盾」節が本書を名指しで指摘している）。
**ここは矛盾したまま残っている。** 本節はその指摘への現時点の回答であり、段階表の書き換えではない。

現時点で見えている交点は2つ。**どちらも未着手・未検証。**

| 交点 | 中身 | なぜ効くか |
|---|---|---|
| **蒸留**（8B教師 → 0.6B級生徒） | 汎用性を捨てて自分の用途に絞り、規模を落とす | 計算量そのものが減る唯一の道。MLX の `LLMRegistry` に 0.6B / 1.7B / 4B / 8B が揃っており、**教師と生徒を同一フレームワーク・同一機体で扱える** |
| **LoRA でシステムプロンプトを重みへ焼き込む** | 毎ターン払っている説明トークンを消す | **一度払って二度と払わない。** 文脈注入500トークンは1,000ターンで約57分（VISION の試算）。アプリの毎ターン system は現状+97トークン（概算・実測未取得） |

**訂正の記録**: 当初「LoRA は計算量を変えないのでエネルギー目標に無関係」と書いていたが、
これは不完全だった（VISION.md 2026-08-16 追記）。1トークンあたりのコストは変わらないが、
**払うトークンの本数を減らせる。** トラックBがエネルギー目標に貢献する正当な道が1本ある。

**未決**: 蒸留を段階表のどこに入れるか（M2 と M3 の間か、別系統か）は決めていない。
訓練データの設計（第6章）と評価基盤（第3章）が先に要るため、
**着手はどちらも整ってからにする。**

### M0: プロンプト・パラメータ設計 ─ **完了**

`modelfiles/` に用途別のシステムプロンプトとパラメータを定義済み。
最も費用対効果が高く、モデルを触る前にやり切るべき段階。

> **この成果はアプリへ自動では届かない。** `modelfiles/` は Ollama 側の資産であり、

### M1: モデルマージ ─ **トラックB の次段階**

複数モデルの重みを数学的に合成する。**学習を伴わないのに、新しい重みができる。**

- ツール: mergekit（CPUで動作。逐次読み込みで16GBでも実行可能）
- 例: Qwen3-8B の言語能力 + Qwen2.5-Coder の実装能力を1つの重みへ統合
- 所要: 1回あたり数十分。**失敗しても0円**なので試行回数を稼げる

**トラックBの最初にここを通す理由**: 学習データを用意せずに「新しいモデルを作って評価する」
サイクルを一周できる。評価基盤（第3章）の慣らし運転を兼ねる。

> **プロジェクト全体の次の作業ではない。** 全体の作業順は第5章を見ること。
> 現在の主戦場はトラックA（A1 の完成条件検証と MLX の実測）にある。

### M2: LoRA/QLoRA → fuse

自分のデータでモデルを微調整し、その差分をベースへ融合して単一モデルにする。

- ツール: MLX（`mlx_lm.lora` で学習 → `mlx_lm.fuse` でベースへ融合）
- 開発機（M3/16GB）で **7〜8B の QLoRA が射程内**。ただし上限に近い
- 必要データ: 質の揃った例が **数百〜数千件**
- 所要: 1回あたり数時間

**この段階の成果物は、技術的にも実務的にも「新しいモデル」。**
`mlx_lm.convert` で MLX形式にすれば、[DESIGN.md](DESIGN.md) 第7章の経路C
（ローカルディレクトリ読み込み）でそのままアプリに載せられる。

> **GGUFへの変換工程が消えた。**（2026-08-16）
> 学習を MLX で行い、推論も MLX で行う以上、出力は最初から MLX が読める形式になる。
> **推論と学習が同じフレームワーク上に載ったことが、この工程を不要にした。**
> なお **`mlx-swift-lm`（Swift側）に学習APIがあるかは調査していない【未確認】。**
> 当面は Python の `mlx-lm` を使う想定。

**ここでローカルの天井に当たる。** 1回の学習に半日以上かかるようになり、
試行回数が稼げなくなった時点が移行の合図（第4章）。

この段階で**評価基盤を必ず完成させる**。理由は第4章。

## 3. 評価基盤（両トラックの前提）

**モデルを変えるより先に、良し悪しを判定する仕組みが要る。**
これが無いまま次段階へ進むと、改善したのか悪化したのかが分からなくなる。

| 種類 | 対象 | 手段 | 状態 |
|---|---|---|---|
| 生成速度 | Ollama（GGUF） | `make bench` → [BENCH_RESULTS.md](BENCH_RESULTS.md) | **基準値取得済み** |
| 入力処理速度 | Ollama（GGUF） | `scripts/bench-prompt.py` | **こちらが正**（下記） |
| 生成速度・TTFT | **アプリ（MLX）** | `make app-stats` → `logs/mlx-stats.log` の `[STATS]` 行 | **2往復のみ**（Debug）。基準値は未取得。**2往復目で TTFT が崩れる問題を先に切り分ける** |
| 品質 | 両方 | 自分の実作業を題材にした評価セット | **設計済み・未実装**（[DESIGN.md](DESIGN.md) 第15章）← M1着手前に作る |

> **2026-08-17、品質の評価基盤を設計した**（[DESIGN.md](DESIGN.md) 第15章）。
> **適応度関数（品質 ÷ 消費エネルギー）の分母だけが測れて、分子がゼロという非対称**を
> 埋めるためのもの。原則は4つ ── **絶対評価せず対比較にする / 目隠しで比べる /
> n=1 で判定しない / 題材は実際に困っている作業にする。**
> 最初の比較対象は **8B vs 4B**（VISION 第2因子であり、16GB機の性能問題の解でもある）。

**`make bench` の「入力処理 tok/s」列は偽値。無効。**（2026-08-16 判明）
同一プロンプトを繰り返すためプレフィックスキャッシュに全命中し、
実計算がほぼゼロなのに全トークンを数えるため、割り算した tok/s だけが膨らむ。
**`scripts/bench.py` 側は未修正のまま。** 入力処理の真値は `bench-prompt.py` の結果を使うこと
（詳細は [BENCH_RESULTS.md](BENCH_RESULTS.md) 冒頭の「読み方の注意」）。

**アプリ（MLX）側は2往復ぶんの数字があるだけで、基準値と呼べるものはまだ無い。**
Debug ビルド（デバッガは非接続）・思考ON の連続2往復
（decode 19.46 → 19.21 tok/s / TTFT **0.97 → 11.87秒** / ピーク4,615 → 4,656MB。
詳細は [DESIGN.md](DESIGN.md) 2.6節）。**Release・デバッガ非接続で取り直すまで基準値にしない。**

> **⚠️ そのまえに切り分けるべき問題がある。** 2往復目で**プリフィルだけが9.2倍崩れ**、
> TTFT が 0.97秒 → 11.87秒 になっている（**デコードは無傷**）。
> **NFR-03 は2往復目で破れており、体感速度を支配するのはこちら。**
> 原因未特定。仮説と切り分け方は [BENCH_RESULTS.md](BENCH_RESULTS.md) 2026-08-17 の節。
> **速度のつまみを回す前に、これを先に潰すこと。**

`make bench` は Ollama の `sophia-chat` / `sophia-coder` しか叩かず、アプリには届かない。
両者はモデル形式も量子化方式も別系統なので、**Ollama の実測値をアプリの性能として読まないこと。**

> **計測経路の落とし穴（実測で判明）**: `make app-run`（= `open`）では
> `[STATS]` 行が1バイトも残らない。LaunchServices 経由で fd 0/1/2 が /dev/null に繋がるため。
> 生の `write(2)` なので `log stream` でも拾えない。
> `make app-stats` が `open --stderr` で fd 2 をログへ付け替える。

### 速度計測で判明した注意点（実測）

ファンレスのため、**同一条件でも実行順で結果が最大2倍変わる**。

| 実行順 | sophia-coder | sophia-chat |
|---|--:|--:|
| chat先行 | 9.0 tok/s（2番目） | 13.4 tok/s（1番目） |
| coder先行 | 14.1 tok/s（1番目） | 7.0 tok/s（2番目） |

**先に走った方が速い。** 比較計測は本体が冷えた状態に揃えて行うこと。
連続使用時の実力値は **7〜9 tok/s** と見ておく（いずれも Ollama 側の値）。

**ただし原因を熱制限だけに帰すのは早い。** その後の計測で、この機体では
**メモリ逼迫（ページング）の方が大きな雑音源**であることが分かった
（同一条件16件で31.7〜154.5秒、4.9倍の開き）。
**連続実行での劣化が熱かページングかは、まだ切り分けていない【未確認】。**

さらに 16GB機では**アプリ（重み4.6GB + KV等で約5.4GB常駐見込み）と Ollama を同時に動かせない。**
比較計測をするときは、片方を必ず終了させること。

## 4. クラウド移行の判断条件

以下の**いずれか2つ以上**を満たした時点で移行を検討する。

| # | 条件 | 意味 |
|---|---|---|
| 1 | 学習1回に**12時間以上**かかるようになった | 試行回数が稼げず、改善が止まる |
| 2 | 訓練データが**1万件**を超えた | ローカルの計算量では回し切れない |
| 3 | LoRAのrankやデータを増やしても**改善が頭打ち**になった | 手法の限界。次はベースモデル自体を鍛える段階 |
| 4 | 7〜8Bの**表現力不足が評価結果で示された** | モデル規模を上げる必要がある |

### 前提条件（必須）

**第3章の品質評価基盤が完成していること。**

これが無いままクラウドへ移ると、支払った費用で何が良くなったのか判定できない。
**移行してよいかを決めるのは、金額ではなく測定能力。**
条件1〜4を満たしても評価基盤が無ければ、先に評価基盤を作る。

### 移行時に見直すもの

- ベースモデルの再選定。**現行の `Qwen/Qwen3-8B` と `mlx-community/Qwen3-8B-4bit` は
  どちらも apache-2.0 で確認済み**（[MODELS.md](MODELS.md)）だが、**規模を上げて別系統に移るなら
  ライセンスは必ず引き直すこと**
- 学習データの権利関係
- 推論はローカルのまま維持する方針の再確認（本書冒頭）

## 6. 最大の障害

**計算資源ではなくデータ。**

M2以降で意味のある差を出すには、質の揃った訓練データが数千件必要になる。
GPUは金で買えるが、データは自分で作るしかない。
着手時は「何を、どう集め、どう整形するか」から設計すること。

この観点では、**日々の実作業のログを今から残しておくことが最も安価な投資**になる。
