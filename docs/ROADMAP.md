## 基本方針

**ローカルは終点ではなく出発点。** 0円で回せる範囲で性能を上げ続け、
**ローカルの天井に当たった時点でクラウドへ移行する。**

移行は「いつか考えること」ではなく、**あらかじめ条件を決めておく判断**として扱う。
条件は第4章に定義する。

### 2本のトラック

| トラック | 内容 | 依存関係 |
|---|---|---|
| **A: アプリ（器）** | Electron製デスクトップアプリ | モデルの完成を待たない |
| **B: モデル（中身）** | 独自モデルの開発 | アプリの完成を待たない |

**両者は独立して進む。** 接点は「GGUFファイル1個」だけで、
アプリはそれを読むだけの構造にしてある（[DESIGN.md](DESIGN.md) 第4章）。
どちらかが止まっても、もう一方は進められる。

### クラウド移行後も変わらないこと

**推論と配布はローカルのまま。クラウドを使うのは学習だけ。**

```
[クラウド]  学習・微調整  ──→ 完成した重み(GGUF) ──→ [ローカル] 推論・配布
```

学習をクラウドへ移しても、**利用者のデータが外部に出ることはない**。
アプリの価値（NFR-01）はこの分離によって維持される。
つまりクラウド移行は、アプリの設計にもプライバシー要件にも影響しない。

## 2. トラックB：モデル開発

**目標は「自分だけのモデル」＝ 新しい重みを持つモデルを作ること。**
RAGのような外付けの仕組みではなく、モデルそのものを作る。

### 段階

| 段階 | 手法 | 場所 | コスト | 新しい重みができるか |
|---|---|---|---|:--:|
| **M0** | システムプロンプト・パラメータ設計 | ローカル | 0円 | ✗（設定のみ） |
| **M1** | **モデルマージ** | ローカル | **0円** | ✅ |
| **M2** | **LoRA/QLoRA → fuse** | ローカル | **0円** | ✅ |
| **M3** | SFT本格化 + 評価基盤の整備 | ローカル | 0円 | ✅ |
| ── | **移行判断ポイント（第4章）** | | | |
| **M4** | 大規模SFT / DPO | クラウド | 数万〜数十万円 | ✅ |
| **M5** | 継続事前学習 | クラウド | 数十万〜数百万円 | ✅ |
| **M6** | スクラッチ事前学習 | クラウド | 数千万円〜 | ✅ |

> コストは概算。GPU価格は変動するため、着手時に実勢を確認すること。

### M0: プロンプト・パラメータ設計 ─ **完了**

`modelfiles/` に用途別のシステムプロンプトとパラメータを定義済み。
最も費用対効果が高く、モデルを触る前にやり切るべき段階。

### M1: モデルマージ ─ 次の一手

複数モデルの重みを数学的に合成する。**学習を伴わないのに、新しい重みができる。**

- ツール: mergekit（CPUで動作。逐次読み込みで16GBでも実行可能）
- 例: Qwen3-8B の言語能力 + Qwen2.5-Coder の実装能力を1つの重みへ統合
- 所要: 1回あたり数十分。**失敗しても0円**なので試行回数を稼げる

**最初にここを通す理由**: 学習データを用意せずに「新しいモデルを作って評価する」
サイクルを一周できる。評価基盤（第3章）の慣らし運転を兼ねる。

### M2: LoRA/QLoRA → fuse

自分のデータでモデルを微調整し、その差分をベースへ融合して単一モデルにする。

- ツール: MLX（`mlx_lm.lora` で学習 → `mlx_lm.fuse` でベースへ融合）
- 開発機（M3/16GB）で **7〜8B の QLoRA が射程内**。ただし上限に近い
- 必要データ: 質の揃った例が **数百〜数千件**
- 所要: 1回あたり数時間

**この段階の成果物は、技術的にも実務的にも「新しいモデル」。** GGUFへ変換してアプリに載せられる。

### M3: SFT本格化と評価基盤

データを増やし、学習条件を体系的に振る段階。
**ここでローカルの天井に当たる。** 1回の学習に半日以上かかるようになり、
試行回数が稼げなくなった時点が移行の合図（第4章）。

この段階で**評価基盤を必ず完成させる**。理由は第4章。

### M4〜M6: クラウド

| 段階 | 内容 | 規模感 |
|---|---|---|
| M4 | 大規模SFT / DPO | データ数万件。GPU数時間〜数十時間 |
| M5 | 継続事前学習 | 数億〜数十億トークン。GPU数百〜数千時間。**国産モデルの多くがこの手法** |
| M6 | スクラッチ事前学習 | 数兆トークン。**8B級で数千万円〜。組織規模の投資** |

M5まで到達すれば、一般に「独自モデル」と呼んで差し支えない水準になる。
M6は個人の射程外だが、**小規模モデル（100M〜500M）に限れば
学習目的での実行は現実的**な範囲に入る。

## 3. 評価基盤（両トラックの前提）

**モデルを変えるより先に、良し悪しを判定する仕組みが要る。**
これが無いまま次段階へ進むと、改善したのか悪化したのかが分からなくなる。

| 種類 | 手段 | 状態 |
|---|---|---|
| 速度 | `make bench` → `BENCH_RESULTS.md` | **完成** |
| 品質 | 自分の実作業を題材にした評価セット | **未整備** ← M1着手前に作る |

### 速度計測で判明した注意点（実測）

ファンレスのため、**同一条件でも実行順で結果が最大2倍変わる**。

| 実行順 | sophia-coder | sophia-chat |
|---|--:|--:|
| chat先行 | 9.0 tok/s（2番目） | 13.4 tok/s（1番目） |
| coder先行 | 14.1 tok/s（1番目） | 7.0 tok/s（2番目） |

**先に走った方が速い。** 比較計測は本体が冷えた状態に揃えて行うこと。
連続使用時の実力値は **7〜9 tok/s** と見ておく。

## 4. クラウド移行の判断条件

以下の**いずれか2つ以上**を満たした時点で移行を検討する。

| # | 条件 | 意味 |
|---|---|---|
| 1 | 学習1回に**12時間以上**かかるようになった | 試行回数が稼げず、改善が止まる |
| 2 | 訓練データが**1万件**を超えた | ローカルの計算量では回し切れない |
| 3 | LoRAのrankやデータを増やしても**改善が頭打ち**になった | 手法の限界。次はベースモデル自体を鍛える段階 |
| 4 | 7〜8Bの**表現力不足が評価結果で示された** | モデル規模を上げる必要がある |

### 前提条件（必須）

**第3章の品質評価基盤が完成していること。**

これが無いままクラウドへ移ると、支払った費用で何が良くなったのか判定できない。
**移行してよいかを決めるのは、金額ではなく測定能力。**
条件1〜4を満たしても評価基盤が無ければ、先に評価基盤を作る。

### 移行時に見直すもの

- ベースモデルの再選定（規模を上げるならライセンスも再確認 ─ 未決事項#4）
- 学習データの権利関係
- 推論はローカルのまま維持する方針の再確認（本書冒頭）

## 6. 最大の障害

**計算資源ではなくデータ。**

M2以降で意味のある差を出すには、質の揃った訓練データが数千件必要になる。
GPUは金で買えるが、データは自分で作るしかない。
着手時は「何を、どう集め、どう整形するか」から設計すること。

この観点では、**日々の実作業のログを今から残しておくことが最も安価な投資**になる。
