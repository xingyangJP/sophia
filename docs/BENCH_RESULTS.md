# ベンチマーク履歴

`make bench` の結果を時系列で残す。設定を変えたときに「本当に速くなったか」を後から確認するための記録。

## 読み方の注意（重要）

1. **実行順で結果が最大2倍変わる。** ファンレスのため、後に実行したモデルほど
   熱制限を受けて遅くなる（2026-08-15 12:10 の検証を参照）。
   **異なる計測を比較するときは、実行順と本体の温度状態を揃えること。**
2. **TTFT が `nan` は「本文に到達しなかった」を意味する。** 思考モードのモデルで
   生成上限に達し、思考だけで打ち切られた場合に発生する。
3. 表の TTFT は**本文が出始めるまで**の時間。思考テキストは含まない。
   利用者の体感（何かが表示されるまで）とは別の指標。
4. **`bench.py` が出す「入力処理 tok/s」は偽値。無効。**（2026-08-16 判明）
   同一プロンプトを繰り返すためプレフィックスキャッシュに全命中し、
   実計算がほぼゼロなのに `prompt_eval_count` は全トークンを数えるため、
   割り算した tok/s だけが何十倍にも膨らむ。
   **下記 2026-08-15 の2つの節にある「入力処理 tok/s」列（3,081〜4,171）は
   すべて無効。性能指標として使わないこと。**
   入力処理の真値は 2026-08-16 16:05 の節を見ること（114〜167 tok/s）。
5. **メモリ逼迫が最大の雑音源。** 空きメモリが少ない回はページングで最大4.9倍遅くなる。
   2026-08-16 以降の節にある「空きMB」「ページイン」列を必ず併読すること。
   ページインが数千を超える行は外れ値として扱う。

**当初の問題設定「入力処理速度が計測ごとに25倍違う（3,610 vs 140 tok/s）」は、
前提が誤っていた。** 検証した4つの仮説の結果:

| # | 仮説 | 結果 |
|---|---|---|
| 1 | `OLLAMA_KV_CACHE_TYPE=q8_0` が Metal で入力処理を大幅に遅くしている | **否定。** f16 が約6%速いだけで、機体のばらつき（同一条件で最大4.9倍）に埋もれる。25倍の説明にはならない |
| 2 | 512トークンごとにKVキャッシュを捨てて再計算している | **否定。** `cached n_tokens` は512ずつ**増えて**おり、チャンク処理の記帳。実計算 4,560 = 4,793 − 233（キャッシュ命中）が厳密に一致する |
| 3 | 140 tok/s が異常に遅い | **否定。** これがこの機体の素の実力値。異常なのは 3,610 tok/s の側で、プレフィックスキャッシュ命中を入力処理として計上した偽値（59 TFLOP/s 相当＝理論ピークの9倍） |
| 4 | `num_batch` 512 が律速している | **判定不能。** ばらつきが条件差より大きく、512 と 1024 を区別できなかった |

**残った真の原因は、設定ではなくプロンプト長そのもの。**
Open WebUI が「こんにちは」の一言に4,786トークン送っており、
そのうち約4,550トークン（95%）がビルトインツール定義の自動注入だった。
入力処理は正常に約140 tok/s で動いており、**4,786トークンなら32〜35秒かかるのが正しい挙動**。

→ 対処は `.env` と TUNING.md 第2章へ反映済み。
→ 対策後の再計測では、速度を比べる前に必ず `logs/ollama.log` の
  `task.n_tokens` を見て入力長が実際に減ったことを確認すること。

### この計測で判明した、計測手順そのものの問題

1. `scripts/bench.py` の「入力処理 tok/s」は偽値（上記「読み方の注意」4）
2. `num_batch` を固定しないと Ollama が起動ごとに違う値を選ぶ
   （未固定の起動6回で `-b 512` が5回、`-b 1024` が1回。空きメモリ最大の回だけ1024）
3. メモリ逼迫が熱より大きい雑音源。1回の計測中にページアウト90,104ページ（約1.4GB）が
   発生したブロックがあり、そのブロックだけ全長で速度が半分になった
4. 冷却なしの連続実行で中央値1.55倍遅くなる（8ブロックの比: 1.00〜3.47倍）。
   熱とページングの両方が混ざっており、**どちらが主因かは切り分けていない**

### この計測の最大の発見 — プリフィルだけが崩れる

**デコードは無傷（19.46 → 19.21 tok/s）なのに、プリフィルだけが崩れている。**
全体的な熱制限なら**デコードも道連れになるはず**で、そうなっていない。

> **「9.2倍」と「13.9倍」を別々の証拠として数えないこと**（初版はそう書いていた。撤回する）。
> **`prefill_tps` は独立した測定値ではなく `in ÷ prefill_s` の再掲**である
> （MLX 側で `promptTokenCount / promptTime` として計算される）。
> 実測値は `prefill_s` の 0.84秒 → 11.65秒 の1つだけで、残りはその言い換えにすぎない。

#### 決定的な数字 — 2往復目は「計算していない」

1トークンあたりの単価に直すと、原因の性質が絞れる。

| | プリフィル | デコード |
|---|--:|--:|
| 1往復目 | **8.1 ms/tok** | 51.4 ms/tok |
| 2往復目 | **74.7 ms/tok** | 52.1 ms/tok |

**2往復目は、プリフィルの1トークン単価がデコードを上回っている。**
プリフィルは重みの読み出しを156トークンで償却できるぶん、**計算律速なら単価はデコードより
必ず安くなる**（1往復目はまさにそうで、6.4倍安い）。**それが逆転しているということは、
11.65秒の大半は演算ではない。**

**入力長そのものも説明にならない。** 104→156トークンは1.5倍でしかない。

> **⚠️ この節の初版は「ピークメモリも+40MBしか動いていないのでメモリ不足では説明がつかない」と
> 書いていた。これは誤りだったので撤回する。**
> `peak_mb` は生成ごとに `MLX.Memory.peakMemory = 0` でリセットされる
> **「その生成中のピーク*アロケーション*量」**である（`MLXEngine.swift:290`）。
> MLX の会計はアロケーション量であって、**そのページが物理RAMにあるかスワップにあるかを
> 一切知らない。4.6GB 全部がスワップに出ていても値は変わらない。**
> したがって `peak_mb` が動かないことは、**KVの膨張は否定できるが、ページアウトは否定できない。**
> **residency を測るには OS 側（`phys_footprint` / ページイン数）を見るしかない。**

#### 有力仮説: 待機中に重みがページアウトされ、プリフィルが読み戻しの代金を払った

**コード調査で、この仮説の前提条件がすべて満たされていることを確認した。**

| 確認したこと | 根拠 |
|---|---|
| **重みは wired されていない** ─ macOS から見て追い出せる普通のページ | `generate(...)` の `wiredMemoryTicket` が既定 nil。MLX の公式ドキュメントは `kind: .reservation` を「モデルの重みのような長寿命メモリ用」と明記 |
| モデルは往復をまたいで保持されている（**都度ロードではない**） | `MLXEngine.swift:39` の `container`、同 `:167` で同一モデルなら即 return |
| 往復の合間に `clearCache()` は呼ばれない | 呼び出し元はモデル切替時のみ（`MLXEngine.swift:177`） |
| **`prefill_s` の計測窓が「待機後に4.6GB全体へ最初に触る一回」と正確に一致する** | MLX 側 `promptPrefillTime` はプロンプト全体の全層 forward。`decode_s` は2トークン目以降＝すでに常駐 |
| メモリ圧への反応が一切ない | memory pressure ハンドラ・背景遷移時の解放とも0件 |
| `cacheLimit` が 20MB と小さい | `ChatOptions.swift:139`。1往復目終了時に KV と中間バッファは**OSへ返る**。2往復目はそれを取り直す |

**`prefill_s` に別の作業が混入している線は潰れた。** 計測窓に含まれるのは
プロンプト全体のフォワードパスだけで、**モデルのロード・チャットテンプレート適用・
トークナイズ・KVキャッシュ確保はいずれも窓の外**である。
独立した裏付けがログ自身にある ─ `ttft_s` の起点は `prefill` より前なので、その差が
窓外の全コストの上限になる:

| | ttft_s | prefill_s | 差＝窓外の全コスト |
|---|--:|--:|--:|
| 1往復目 | 0.97 | 0.84 | **0.13秒** |
| 2往復目 | 11.87 | 11.65 | **0.22秒** |

**窓の外は合計0.22秒以下。11.65秒は本当にプロンプトのフォワードパスの壁時計である。**

**桁の整合（計算であって証拠ではない）**: 1往復目と同じ123.26 tok/s なら156トークンは1.27秒。
実測11.65秒との差は約10.4秒。4.6GB を10.4秒で戻すと **約440 MB/s** ─
圧縮スワップの伸長＋NVMe 読みとしてありうる桁である。
**ただし他プロセスとのメモリ争奪でも同じ桁が出るため、これだけでは決められない。**

#### 残る候補

| # | 仮説 | 状態 | 見分け方 |

| 1 | **待機中のページアウト** | **本命** | 手順は下記。ページイン数が跳ねれば確定 |

#### KVキャッシュは持ち越されていない（確定）── ただし主因ではない

`MLXEngine` が呼ぶ `generate(input:parameters:context:components:)` は **`cache:` を渡しておらず**、
MLX 側は毎回 `model.newCache(...)` で**全36層ぶんの新規キャッシュ**を作る。
エンジンは `[KVCache]` も `LMOutput.State` も保持していない。
`ChatViewModel` は毎ターン system + 完了済みの全ターンを再送している
（**思考テキストは再送していない** ─ 入力トークンの増分52がその内訳と一致することで裏が取れた）。

**しかしこれは今回の主因ではない。** 156トークンを1往復目のレート（123.26 tok/s）で
全部再プリフィルしても1.27秒で、**11.65秒の11%にしかならない。**

> **とはいえ、放置してよい問題ではない。**
> 毎ターン全再プリフィルは、会話が伸びるほど**二乗で効く実在の税**である。
> 直す形は `MLXEngine` actor に `[KVCache]` + `LMOutput.State?` + トークン台帳を持たせ、
> `generate(input:cache:state:...)` へ渡すこと。
> **`ChatSession` をそのまま使ってはいけない** ─ 中断したターンが履歴に残らないという
> FR-02 の要件と衝突するため、台帳は自前で持つ必要がある。

#### 併せて見つかった構造的な無駄 — `lm_head` が全位置に適用されている

MLX の Qwen3 実装は最終隠れ状態の**全位置**に `lm_head` を掛けており、
プロンプトのフォワードで `[1, L, 151936]` のロジットを実体化する
（bf16 で 104トークン→約31.6MB / 156トークン→約47.4MB）。**使うのは最終行だけである。**
どちらも `cacheLimit` の20MBを超えるためバッファキャッシュに載らず、**毎回 Metal から新規確保**になる。

**これは上流ライブラリの実装であってアプリ側のコードではない**ので、すぐには直せない。
ただし**会話が伸びるほど線形に効く**ため、記録しておく。

#### ⚠️ 直す前に、まず再現するかを確かめること

**この11.65秒は、アプリの性質ではなく「そのときの機体の状態」を測った数字である可能性が相当ある。**
計測はスワップが 5,120M 中 4,056M 埋まった機体で、**並行作業の最中に**取られている。
**静かな状態で再測定して再現しなければ、直すべきものは何もない。**

#### 白黒つける最短手順（アプリを1行も変えずにできる）

**手順0 — 最も安く効く1手: まったく同じプロンプトを2回続けて送る。**

**入力トークン数が同一**なので、トークン数・会話長・入力長といった変数が全部消える。
**2回目が速ければ、原因はトークン数でも会話長でもなく「初回に触る」側だと確定する。**
（会話履歴が積み上がらないよう、2回目は新しい会話で送るか、同じ問いを繰り返す）

**手順1 — 対照実験。** 同じセッションで3パターンを測る。

- (a) 間を空けず2連続で送信（合間1〜2秒）
- (b) 合間に3〜5分待ってから2往復目
- (c) 待機中に他プロセスのメモリ需要を作る／作らない

**(a) で遅くならず (b) で遅くなれば、ページアウト説を強く支持。** (a) でも遅ければ別原因。
**(a)(b) とも遅くならないなら、当日の並行作業による争奪が主因だったことになる。**

**手順2 — OS 側のページイン数を差分で取る。** 別ターミナルで、
1往復目直後 / 2往復目直前 / 2往復目直後 の3点で:

```
vm_stat | grep -E "Pageins|Decompressions|Swapins"
footprint -p $(pgrep -x Sophia)
```

- 2往復目のプリフィル中に **Pageins / Decompressions が30万〜120万ページ規模で増える**なら
  **確定**（4.6GB ÷ 16KB ≈ 288Kページ、÷4KB ≈ 1.15Mページ）
- ほとんど増えないのに11秒かかるなら**反証**
- `phys_footprint` が待機中に落ちて2往復目で戻れば、これも決定的

> **Instruments は使わないこと。** この機体では観測行為自体が対象を壊す。

**手順3 — アプリに足すなら**（要ビルドなので後回し）:
`MLX.Memory.snapshot()` を足しても**無駄**（residency を測らないため）。
`task_info(mach_task_self_, TASK_VM_INFO, ...)` の `phys_footprint` と、
`TASK_EVENTS_INFO.pageins`（**プロセス内で取れる。sudo 不要**）を
**prefill 直前・直後**で出す。これなら1往復で白黒がつく。
`GenerationStats` は struct なのでフィールド追加で既存コードは壊れない。

#### 計測ハーネスの形（調査済み）

**GUI を介さずエンジンを N 往復駆動することはできる。ただし XCTest に限る。**

| 方式 | 可否 | 理由 |
|---|---|---|
| 単発の `swift script` | **不可** | `swift build` では `.metallib` が生成されず MLX 推論が動かない。既存の `scripts/test-*.swift` は MLX 非依存の文字列テスト専用 |
| **`SophiaTests` に probe を足す** | **可** | テストターゲットの `TEST_HOST` が `Sophia.app` で、テストバンドル内に `default.metallib` が実在する。**モデル重みも同じサンドボックスコンテナにあるので再ダウンロード不要。** タイムアウトも無効化されており900秒の待ちを入れられる |

推奨する形は **`build-for-testing` を1回 → 条件ごとに `test-without-building`**。
条件は `.xctestrun` を複製して環境変数を書き換えて注入する。
**ビルドが計測に混ざらない**（`app-stats` をビルドに依存させなかったのと同じ理由）、
出荷物が汚れない、CLI 実行なのでデバッガが付かない。
実装は新規2ファイル＋既存3ファイルへの軽微な追加で、**実装約5時間＋実行3〜4時間**（待ち時間が支配的）。

> **ただし、最初にやるべきは実装ゼロの30分スモークである。**
> 別窓で `vm_stat` / `footprint` を2秒ごとに記録しながら、従来どおり `make app-stats` で2往復する。
> **2往復目のプリフィル区間に Pageins のスパイクが乗るかを見るだけ。**
> ここで見えれば5時間の実装に入る前に本命がほぼ確定し、作るものを絞れる。
> **そして何より、9.2倍がそもそも再現するかをここで確かめられる。**

**実験計画の全体**（E1〜E7 の条件と判定基準）は別途スクラッチに置いてある。要点:

| # | 条件 | 判定基準 |
|---|---|---|
| E1 | 同一入力を待ち0秒で5回 | 1回目だけ遅い→初回コスト / 全部同じ→初回コスト却下 |
| E3 | 待ち **0/30/60/300/900秒** | プリフィルがアイドル時間と単調増加、かつ pageins 大 → **ページアウト説を確定** |
| E4 | 待ち中に8GBを能動注入 | 注入時だけ崩れる → **因果として確定**（E3 の相関より強い） |

### NFR への影響

**根本は「生成中のワーキングセットが約9GB ある」ことである。** モデルの4.6GBではない。

生成中の実測内訳（`footprint -p`）:

```
8952 MB   IOAccelerator (graphics)     ← ここが本体
  70 MB   MALLOC_SMALL
  44 MB   Owned physical footprint (unmapped) (graphics)
  40 MB   MALLOC_LARGE
--------
9128 MB   合計
```

**モデル4.6GBに対し、GPU確保が9GB近い。** 余分な約4.4GBが何であるかは**まだ説明できていない**が、
mmap でも malloc でもなく **Metal のバッファ**であることは確定した
（safetensors の読み込みは `ParallelFileReader` の `read()` で mmap ではない）。

そして連鎖はこうなる:

1. **生成中のワーキングセットが約9GB。** 16GB機で他のアプリが動いていれば収まらない
2. **アイドルすると OS が追い出す**（60秒で2.36GB を swapout）
3. **次のプリフィルで戻そうとするが、収まらないので出し入れを繰り返す** → 20GB の往復
4. デコードは、その時点で必要な分が常駐に戻っているので**無傷**

**「アイドル起因（A）か、容量起因（B）か」という当初の二分法は誤りだった。**
**引き金がA、被害の大きさを決めているのがB である。**

### 対処の方向が変わる

**重みを wired にする案は使えない。** 9GB を16GB機で wired にすれば他が死ぬ。

**効くのはワーキングセットを減らすことである** ─ すなわち
**[VISION.md](VISION.md) 第2因子（難易度に応じてモデルを選ぶ）が、
省エネの話であると同時に、いま目の前の性能問題の解でもある。**

| 対処 | 効き方 |
|---|---|
| **余分な4.4GBの正体を突き止めて削る** | **最優先。** 効けば9GB→5GB弱になり、収まる可能性がある |
| 小さいモデル（4B / 1.7B）を既定にする | 確実に効く。VISION 第2因子そのもの |
| KV量子化・`maxKVSize` | 効くが、この規模の差には足りない見込み |
| プリフィル進捗の表示 | 直さないが、65秒の無言は避けられる |

### ⚠ 計測手法についての重要な発見 — **3つ目の指標も外れた**

**`TASK_EVENTS_INFO.pageins` は、この現象を数えない。**
3往復目のプロセス内 pageins は **25** だったが、同じ区間で系全体は **1,253,872 swapin** している。

**これで測れなかった指標が3つになった:**

| 指標 | なぜ外れたか |
|---|---|
| `MLX.Memory.peakMemory` | アロケーション量。residency を知らない |
| `RSS` | **`IOAccelerator (graphics)` を数えない** |
| `TASK_EVENTS_INFO.pageins` | **compressor の伸長と GPU メモリのフォルトを数えない** |

**唯一機能したのは `vm_stat` の系全体の `Swapins` / `Swapouts` である。**
`scripts/probe-watch.sh` がこれを別経路で記録していたから判定できた。
