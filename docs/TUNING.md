# チューニングガイド（MacBook Air M3 / 16GB 前提）

このファイルは「性能を上げたくなったとき、どのつまみを回すか」の一覧。
上ほど効果が大きい。**1つ変えたら `make bench` で測る**。同時に複数変えると、
何が効いたのか分からなくなる。

---

## 0. まず前提：16GBの予算表

Apple Silicon はメモリをCPU/GPUで共有している。モデルに回せるのは全体ではない。

| 用途 | 消費 |
|---|--:|
| macOS 本体 + 常用アプリ（ブラウザ等） | 4〜6 GB |
| Ollama + Open WebUI | 約 1 GB |
| **モデルに回せる実質枠** | **約 9〜10 GB** |

モデルの必要量は「重み + KVキャッシュ」。KVキャッシュは `num_ctx` に比例して増える。

| モデル規模 | Q4_K_M の重み | +KV(8k) | 判定 |
|---|--:|--:|---|
| 4B | 約 2.6 GB | 約 3.0 GB | 余裕。下書き・分類など軽作業向き |
| 7〜8B | 約 4.7 GB | 約 5.4 GB | **常用の最適解** |
| 12B | 約 7.3 GB | 約 8.2 GB | 動くが、他アプリを絞る必要あり |
| 14B | 約 8.5 GB | 約 9.5 GB | ギリギリ。ブラウザを閉じる前提 |
| 27B以上 | 15 GB〜 | — | 不可。スワップして実用速度にならない |

枠を超えると macOS がスワップを始め、tok/s が数分の1まで落ちる。
「遅い」と感じたら、まず `ollama ps` と アクティビティモニタの
**スワップ使用領域** を見ること。ここが増えていたらモデルが大きすぎる。

## 1. 入力プロンプトの長さ（効果：特大 / **実測で最大のつまみ**）

2026-08-16 の切り分け計測で判明した、**このプロジェクトで最も効く一手**。
サーバ側の設定をどう回しても、入力が長ければ待ち時間は縮まない。

### 実測: プロンプト長と入力処理（プリフィル）時間

`sophia-chat` / `num_ctx=8192` / KV `q8_0` / `num_batch=512` / 計測前に90秒冷却 /
毎回プロンプト先頭に nonce を入れてプレフィックスキャッシュを無効化。

| 入力トークン | 処理時間 | tok/s | 1トークンあたり |
|--:|--:|--:|--:|
| 273 | **1.6 s** | 167 | 5.98 ms |
| 1,022 | **4.8 s** | 163 | 6.13 ms |
| 4,792 | **34.3 s** | 133 | 7.52 ms |
| 7,688 | **65.2 s** | 114 | 8.74 ms |

**速度は一定ではなく、長いほど1トークンあたりが高くつく。**
アテンションが「それまでの全文脈」に対して働くため、総時間は長さに対して超線形に伸びる。
同一リクエスト内で測った区間速度がそれを直接示している（7,688トークンのプリフィル1本）:

| 文脈位置 | 2,048 | 3,072 | 4,096 | 5,120 | 6,144 | 7,168 |
|---|--:|--:|--:|--:|--:|--:|
| 区間 tok/s | 157 | 132 | 119 | 107 | 99 | 91 |

### 入力の予算

上の実測点から内挿すると、1,022〜4,792トークン区間の限界速度は約128 tok/s。
そこから逆算した上限（**内挿による見積り**であって実測点ではない）:

| 目標 | 入力の上限 |
|---|--:|
| プリフィル10秒以内（冷間） | 約 1,600 トークン |
| プリフィル10秒以内（連続使用時も守る） | 約 1,000〜1,200 トークン |
| プリフィル5秒以内（冷間） | 約 1,100 トークン |

連続使用時は熱とページングで**中央値1.55倍**遅くなる（8ブロックの1回目→2回目比: 1.00〜3.47倍）。
冷間の数字だけで設計すると、実利用で破綻する。

日本語の目安は概ね **1文字 ≒ 0.5トークン**（本計測時の実測校正値）。
5,000字の文章を貼ると約2,500トークン、プリフィルだけで**冷間16秒前後**かかる。

## 2. クライアントが注入するプロンプト（効果：特大 / **盲点**）

第1章の予算は、利用者が打った文字数ではなく**実際にモデルへ届くトークン数**で決まる。
そしてクライアントは黙って大量に注入してくる。

**実測: Open WebUI 0.11.0 経由で「こんにちは」の一言を送ると 4,786トークンになる。**
素の Ollama API へ同じ入力を送ると245トークン。**差の約4,550トークン（95%）はクライアント由来。**

正体は、Open WebUI が native function calling 用に自動注入する
**ビルトインツール32個のJSONスキーマ**。システムプロンプトでもRAGでもない。
（`utils/middleware.py:2643-2649` で `use_builtin_tools` が立ち、
`utils/payload.py:321-322` でそのまま Ollama のペイロードへコピーされる。
qwen3 のチャットテンプレートが `.Tools` をシステムメッセージ内に展開する。）

内訳（qwen3 の実トークナイザによる計算値。実測ではない）:

| カテゴリ | ツール数 | 概算トークン | 環境変数で止められるか |
|---|--:|--:|---|
| memory | 8 | 1,040 | ✅ `ENABLE_MEMORIES=False` |
| knowledge | 7 | 1,033 | ❌ 存在しない |
| calendar | 4 | 844 | ✅ `ENABLE_CALENDAR=False` |
| automations | 5 | 815 | ✅ `ENABLE_AUTOMATIONS=False` |
| notes | 4 | 382 | ✅ `ENABLE_NOTES=False` |
| tasks | 2 | 254 | ❌ 存在しない（2通目以降のみ付く） |
| time | 2 | 247 | ❌ 存在しない |
| chats | 2 | 207 | ❌ 存在しない |
| code_interpreter | 1 | 87 | ✅ `ENABLE_CODE_INTERPRETER=False` |
| 「# Tools」定型文 | — | 88 | ❌ |

### 対処（効果の大きい順）

1. **モデルの capability「Builtin Tools」を off にする**（本命）
   Open WebUI の Workspace → Models → `sophia-chat` → Capabilities のチェックを外す。
   注入がまるごと止まり、**4,786 → 約231トークン**。プリフィルは34秒 → 約1.5秒。
   代償: ナレッジ検索・ノート・カレンダー・メモリ等のツール機能が全て使えなくなる。
   純粋なチャット/文章作成用途なら実害は小さい。

2. **`.env` の `ENABLE_MEMORIES` / `ENABLE_CALENDAR` / `ENABLE_AUTOMATIONS` / `ENABLE_NOTES` を False**
   **4,786 → 約1,600トークン**が環境変数だけで到達できる下限。
   knowledge / time / chats / tasks には対応する環境変数が存在しないため、ここで頭打ちになる。

3. **1回だけ試すなら** Chat Controls の Advanced Params で
   Function Calling を「Default (Legacy)」にして送信する。設定を作らずに同じ効果が出る。

### ⚠ 環境変数が黙って無視される罠

Open WebUI は設定を DB（`config` テーブル）に保存し、
**環境変数は「DBにまだ行が無いキー」にしか適用されない**
（`models/config.py:256` `if key not in existing_keys`、docstring に
`Existing DB values take precedence over defaults.`）。
初回起動でDBに行ができた後は、`.env` を書き換えて再起動しても**何も変わらない**。

`.env` に `ENABLE_PERSISTENT_CONFIG=False` を入れると `Config.get` がDBを読まなくなり
（`models/config.py:141-142`）、`.env` が権威になる。導入済み。
副作用として、管理画面での設定変更は再起動で消える。

**対策後は必ず `logs/ollama.log` の `task.n_tokens` を見て、
入力長が実際に減ったことを確認してから速度を比べること。**
「設定したつもりが効いていない」を速度差の議論に持ち込むと切り分け不能になる。

### 自作アプリ側への含意

Sophia 本体（Electron アプリ）はこの構造を持ち込まない。詳細は
[DESIGN.md](DESIGN.md) 第2.2章。**送るトークンは自分で数え、予算内に収める。**

## 3. モデル選択（効果：特大）

一番効くのはここ。量子化を1段落とすより、**用途に合ったモデルに替える方が効く**。

- 日本語の文章作成 → 日本語データを多く学習したモデル（Qwen3 系、Gemma 3 系）
- コード → コード特化モデル（Qwen2.5-Coder 系）。汎用8Bより明確に良い
- 分類・整形・要約のような単純作業 → 4B級で十分。速度が段違い

`docs/MODELS.md` に、試したモデルの評価を残していく。

## 4. 量子化レベル（効果：大）

同じモデルでも `Q4_K_M` / `Q5_K_M` / `Q8_0` でサイズと品質が変わる。

| 量子化 | サイズ比 | 品質 | 使いどころ |
|---|--:|---|---|
| Q4_K_M | 1.0 | 実用上ほぼ劣化を感じない | **既定。まずこれ** |
| Q5_K_M | 約1.2倍 | わずかに良い | メモリに余裕があるとき |
| Q8_0 | 約2倍 | ほぼ無劣化 | 16GBでは7B以下でのみ現実的 |

Q4 未満（Q3, Q2）は日本語の破綻が出やすいので、16GBなら手を出さなくてよい。

```bash
ollama pull qwen3:8b-q5_K_M   # 量子化を明示して取得
```

## 5. KVキャッシュ量子化（効果：**小**。当初の想定は実測で否定された）

> **2026-08-16 改訂。** この節は以前「効果：大 / コスパ最良」「メモリをほぼ半減」と書いていた。
> 実測の結果、**速度・メモリの両方について当初の記述が誤りだった**ため全面的に書き換えた。

### 検証した2つの仮説と結果

| 仮説 | 結果 |
|---|---|
| `q8_0` が Metal で入力処理を大幅に遅くしている | **否定。** 差は約6%で、この機体のばらつきに埋もれる |
| `q8_0` はメモリをほぼ半減する | **否定。** 常駐の差は約0.5GB（8%） |

### 実測（KV型のみを変えた最もクリーンな計測）

4,786トークンの入力 / `num_batch=512` 固定 / 全計測の直前に90秒冷却 / 3ラウンド。

| ラウンド | q8_0 | f16 |
|--:|--:|--:|
| 1 | 34.3 s | 31.7 s |
| 2 | 44.5 s ※ | 32.5 s |
| 3 | 34.5 s | 32.5 s |
| **中央値** | **34.5 s** | **32.5 s** |

※ ページイン7,209を伴う外れ値。

**f16 の方が約6%速い。** 差は文脈が長いほど開く（区間速度: 位置2,048で+6%、4,096で+12%）。
つまり「q8_0 が遅い」は方向としては正しいが、**桁が違う話ではなく、犯人でもなかった**。

### メモリの実測

| KV型 | 常駐メモリ |
|---|--:|
| `q8_0` | 6.0〜6.1 GB |
| `f16` | 6.5〜6.6 GB |

差は**約0.5GB**。`num_ctx=8192` では KV 自体が f16 で約1.1GBしかなく、
常駐の大半は重み（Q4_K_M で4.87GiB）が占めるため、「半減」にはならない。
半減するのは KV の部分だけで、全体では8%程度。

### 判断: `q8_0` のまま据え置く

速度で選ぶなら f16 だが、**この機体では0.5GBの方が価値が高い**と判断した。

- 計測中の空きメモリは1.3〜2.8GB、スワップ使用は6〜7GB/8GBで常時逼迫していた
- ページングが起きた計測は最大**4.9倍**遅くなった。6%の速度差より桁違いに大きい
- f16 は常駐が0.5GB大きいぶん、ページングの引き金を引きやすい
  （実際、破滅的な外れ値の2件はどちらも f16 側で出た。ただし q8_0 でも出ている）

**他アプリを閉じて空きメモリに余裕がある使い方をするなら f16 の方が速い。**
`num_ctx` を16384以上に上げる場合は KV が倍になるので、その時点で再判断すること。

※ Flash Attention が有効でないと KV キャッシュ量子化は使えない。セットで入れること
（`OLLAMA_KV_CACHE_TYPE` は `llama-server` の `--cache-type-k` と `--cache-type-v` の
両方に同じ値を渡すため、K/V が別型になる Metal の低速パスには該当しない）。

## 6. num_ctx（効果：大 / 諸刃）

コンテキスト長。**Ollama の既定は小さく、長い会話や長文貼り付けで
古い部分が静かに切り捨てられる**。「途中から指示を忘れる」の主因はほぼこれ。

一方で伸ばすほどメモリを食い、プロンプト処理も遅くなる。用途で決める。

| 用途 | 推奨 num_ctx |
|---|--:|
| 短い対話 | 4096 |
| 文章作成・要約 | 8192 |
| コード（ファイルを貼る） | 16384 |
| 長文書の読み込み | 32768（12B以上との併用は不可） |

Modelfile に焼き込むのが確実（`modelfiles/*.Modelfile` 参照）。

**`num_ctx` は「入れられる上限」であって「毎回その量を処理する」わけではない。**
待ち時間を決めるのは実際に送るトークン数（第1章）。
逆に、上限を超えるとコンテキストシフトが発動して先頭4トークン以外が捨てられ、
以降のターンがほぼ全再プリフィルになる（`n_keep=4` が Ollama の既定）。
`num_ctx=8192` に対して初手で4,786トークン使う状態は、2〜3ターンでこの崖に当たる。
**未検証**: 実際に崖が起きるかは会話を8,192トークン超まで進めて
`logs/ollama.log` に `slot context shift` が出るかで確認できる。まだ確認していない。

## 7. num_batch（効果：不明 / 判定できなかった）

プリフィルを何トークンずつまとめてGPUへ投げるか。Ollama の既定は512。
`logs/ollama.log` に512刻みで出る `cached n_tokens` 行はこれが理由であって、
**KVキャッシュを捨てて再計算しているわけではない**（下記）。

512 と 1024 の A/B を32計測やったが、**同一条件内のばらつきが条件間の差より大きく、判定できなかった**
（4,786トークン16件で31.7〜154.5秒、4.9倍の開き）。結論は出ていない。
判定するにはメモリ逼迫を先に解消してから測り直す必要がある。

**ただしA/Bをやるなら `num_batch` の固定は必須。**
未固定だと Ollama が起動ごとに違う値を選ぶ（未固定の起動6回で `-b 512` が5回、`-b 1024` が1回。
空きメモリが最大だった回だけ1024になった。選択規則は未確認）。
これを固定せずに測ったのが `BENCH_RESULTS.md` の 2026-08-16 13:00 の節で、
KV型の比較として成立していない。

### 「512トークンごとに再計算している」は誤読

以下のログは再計算ではない。`cached n_tokens` は512ずつ**増えて**おり、
チャンクを処理してキャッシュ位置が前進した記帳にすぎない。

```
task 8 | new prompt, n_ctx_slot = 8192, n_keep = 4, task.n_tokens = 4793
task 8 | cached n_tokens = 233,  memory_seq_rm [233, end)
task 8 | cached n_tokens = 745,  memory_seq_rm [745, end)
task 8 | prompt eval time = 37700 ms / 4560 tokens
```

決定的な証拠は最終行。**実計算トークン 4,560 = 4,793（全体） − 233（キャッシュ命中）** で
ぴったり一致する。512ごとに捨てて再計算していれば、この数は数倍に膨らむ。

## 8. モデル常駐の制御（効果：中）

- `OLLAMA_KEEP_ALIVE`（既定5分）— 使うたびに再ロードされるなら伸ばす。
  ただし常駐中はメモリを占有し続ける。`30m` あたりが折衷点
- `OLLAMA_MAX_LOADED_MODELS=1` — **16GBでは必ず1**。
  既定のままだとチャット用とコード用が同時に載り、両方遅くなる
- `OLLAMA_NUM_PARALLEL=1` — 同時実行数。1人で使うなら1が最速

## 9. 生成パラメータ（効果：品質側）

速度ではなく**出力の質**に効く。Modelfile で用途ごとに固定する。

| パラメータ | 文章作成 | コード | 意味 |
|---|--:|--:|---|
| `temperature` | 0.7 | 0.2 | 高いほど多様、低いほど堅実。コードは低く |
| `top_p` | 0.9 | 0.9 | 候補の絞り込み |
| `repeat_penalty` | 1.1 | 1.05 | 同じ表現の繰り返しを抑える |

「同じことを何度も書く」なら `repeat_penalty` を上げる。
「無難すぎる/つまらない」なら `temperature` を上げる。

## 10. システムプロンプト（効果：中 / 手間ゼロ）

**最も費用対効果が高い改善**。モデルを替える前にここを詰める。
役割・読者・文体・禁止事項を書くだけで、出力の当たり外れが目に見えて減る。
`modelfiles/` で管理し、育てたら `make models` で焼き直す。

## 11. MLXバックエンド（効果：中 / Apple Silicon限定）

導入した Ollama は `mlx-c` に依存しており、Apple 純正の MLX を通せる構成。
対応モデルでは Metal 経由より速くなることがある。
ただし全モデルが対応するわけではないので、**必ず `make bench` で前後比較**すること。
速くならないケースもあり、その場合は戻す。

## 12. 熱（効果：特大 / Air特有・**実測で確認済み**）

MacBook Air はファンレス。**連続使用で tok/s が約半分に落ちる**（実測）。

| 実行順 | sophia-coder | sophia-chat |
|---|--:|--:|
| chat先行 | 9.0（2番目） | 13.4（1番目） |
| coder先行 | **14.1（1番目）** | **7.0（2番目）** |

先に走った方が速い。**これはどのつまみを回しても覆せない、最大の変動要因**。
ベンチが前回より遅いときは、設定を疑う前にまず本体の熱を疑うこと。

- **比較計測は必ず冷えた状態に揃える。** 揃えないと計測に意味がない
- 長時間の連続生成は避け、間隔を空ける
- 底面を塞がない（膝上・布の上を避ける）
- 連続使用時の実力値は **7〜9 tok/s**。冷間の13〜14 tok/s は瞬間値でしかない

## 13. 思考モード（効果：特大 / 対応モデルのみ）

`qwen3` 系は応答前に思考テキストを出力する。**体感速度への影響が最も大きいつまみ。**

| 条件 | 思考 | 本文 | 消費トークン | 本文が出るまで |
|---|--:|--:|--:|--:|
| 有効（既定） | 1,075文字 | 112文字 | 300（上限到達） | **15〜29秒** |
| 無効 | 0文字 | 56文字 | 32 | **0.2秒** |

**トークン予算の9割が思考に消える。** 生成上限が小さいと本文に到達せず打ち切られる。

```bash
# 思考を止める（短い質問はこちらが圧倒的に速い）
curl http://localhost:11434/api/generate \
  -d '{"model":"sophia-chat","prompt":"...","think":false}'
```

使い分け:

| 用途 | 思考 | 理由 |
|---|---|---|
| 短い質問・定型作業・翻訳 | **無効** | 待ち時間が消える。品質差はほぼ出ない |
| 複雑な推論・設計相談・デバッグ | **有効** | 思考が効く領域。ただし `num_predict` を1024以上にすること |

**思考モードを有効にしたまま `num_predict` が小さいのが最悪の組み合わせ。**
待たされた末に答えが返ってこない。

### ⚠ `bench.py` の「入力処理 tok/s」は信用しないこと

`scripts/bench.py` が報告する入力処理 tok/s（初期のベースラインで3,610など）は**偽値**。
同一プロンプトをウォームアップ＋計測回で繰り返すため、
2回目以降はプレフィックスキャッシュにほぼ全命中して**実計算がほぼゼロ**になる。
一方 Ollama の `prompt_eval_count` はキャッシュ命中分も数えるので、
割り算した tok/s だけが何十倍にも膨らむ（Ollama の既知の挙動）。

物理的にありえない値であることは算術で確認できる:
2 × 8.19e9 params × 3,610 tok/s = **59 TFLOP/s**。
M3（8コアGPU）の FP16 理論ピークは約6.6 TFLOP/s なので9倍超過している。

**入力処理の真値は 114〜167 tok/s**（プロンプト長による。第1章の表）。
これは理論ピークの33〜41%にあたり、妥当な範囲。
実環境で観測された140 tok/s は異常値ではなく、**これがこの機体の素の実力**。

入力処理を測るときは `scripts/bench-prompt.py` を使う。
毎回プロンプト**先頭**に nonce を入れてキャッシュ命中を壊し、`num_predict=1` で生成を排除し、
`llama-server` の `/tokenize` で実トークン数を合わせている（目標長との誤差±0.2%）。
nonce を末尾に付けると共通プレフィックスが残って無意味になるので、必ず先頭に置くこと。

### 設定変更の前後を比較するときは冷却を入れる

第12章のとおり、冷却なしで複数モデルを続けて測ると**後のモデルが最大2倍遅く出る**。
つまみの効果を見たいのに、熱の差を測ってしまう。

```bash
python3 scripts/bench.py --models sophia-chat --cooldown 120 --save --note "変更前"
# つまみを変える → make restart
python3 scripts/bench.py --models sophia-chat --cooldown 120 --save --note "変更後"
```

さらに厳密に測りたいときは:

- 他のアプリ（ブラウザ・Open WebUI・エディタ）を落とす
- 電源に接続した状態で揃える（バッテリー駆動では省電力制御が入る）
- 同じ順序・同じ時間帯で測る

**絶対値より差分を見ること。** 環境を完全に揃えるのは現実的でないため、
同じ条件で前後を比べる方が判断を誤らない。

### メモリ逼迫が最大の雑音源（2026-08-16 に判明）

この機体では**熱よりページングの方が計測を壊す**。

- 計測中の空きメモリ 1.3〜2.8GB / スワップ使用 6.1〜6.9GB（8GB中）
- 1回の計測中に**ページアウト90,104ページ（約1.4GB）**が発生したブロックがあり、
  そのブロックだけ全長で速度が半分になった
- 同一条件・4,786トークン16件で **31.7〜154.5秒（4.9倍の開き）**

**条件間の差（KV型で6%、num_batch は判定不能）より、同一条件内のばらつきの方が大きい。**
この状態で A/B をやっても何も分からない。設定を比べる前に、まずメモリを空けること。

計測ごとに `sysctl vm.swapusage` と `vm_stat` を記録し、
ページインが多い回は外れ値として扱う。`scripts/bench-prompt.py` は
「空きMB」「ページイン」列を自動で記録する。

### 計測プロトコル（入力処理を測る場合）

1. iOSシミュレータ・Claude.app・ブラウザなど、メモリを食うアプリを閉じる
2. 条件ごとに `ollama serve` を再起動（コールドスタート）
3. 各計測の直前に90秒以上の冷却
4. `num_batch` を明示的に固定する（第7章。固定しないと起動ごとに変わる）
5. 条件の実行順をラウンドごとに入れ替える（順序効果の相殺）
6. 中央値だけでなく最小・最大とページイン数も記録する
