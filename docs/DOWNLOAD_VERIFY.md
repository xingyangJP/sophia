## 何を確かめるのか

**事故の再現条件は既に分かっている**（2026-09-05 の調査）:

```
UI       14,275,517 / 4,622,110,691 bytes で 65秒 停止 → watchdog がキャンセル（-999）
OSログ   同じ HTTP 200 通信が 376,081,675 bytes を受信していた（UI の約26倍）
原因     swift-huggingface 0.9.0 の downloadSnapshot 進捗が大容量ファイル中に更新されない
```

**確かめるのは1つだけ:**

> **`Progress` が止まっている間に、ディスク側の信号が生きていて、打ち切られないこと。**

## 走る前の門（すべて満たすまで走らせない）

| # | 条件 | 判定 |
|---|---|---|
| 0-1 | ビルド／実測を保持している | `XCBBuildService` / `swift-frontend` / `xctest` が 0 件 |
| 0-2 | **単体テストが緑** | `make app-test` が `** TEST SUCCEEDED **`。**印の本数と内訳を控える** |
| 0-3 | **Sophia が起動していない** | `pgrep -x Sophia` が空（**2部起動すると測るのは取得ではなくメモリ争奪になる**） |
| 0-4 | **ログを残す形で起動する** | `make app-watch`（`logs/mlx-stats.log` へ stderr を落とす） |
| 0-5 | **前後で一時ディレクトリの状態を取る** | `du -sh ~/Library/Containers/jp.co.xerographix.sophia/Data/tmp` |

**⚠ 既存の一時ファイル約 7.3GB は削除しない**（利用者の確認が別途要る）。
**観測関数は `modified >= startedAt` で古い残骸を除いているので、消さなくても判定は汚れない**
── **そのこと自体が、この検証で確かめる対象でもある。**

## 判定 —— **データを見る前に決めた**

### 合格（すべて満たすこと）

| # | 条件 | なぜ |
|---|---|---|
| **A1** | **65秒を越えて取得が続く** | 事故は65秒で打ち切られた。**越えたこと自体が第一の証拠** |
| **A2** | `stalled` の行が**出ない** | 打ち切っていない |
| **A3** | ログに **`disk_bytes=` が 0 でない値**で出る | **ディスク信号が武装し、実際に観測できている**（0 のままなら、判定は `Progress` だけで下っている＝直っていない） |
| **A4** | **`disk_bytes` が単調に増える区間がある** | 観測が本物のファイルを見ている |
| **A5** | 取得が完了し、**展開へ進む** | 欠陥2（完了した取得を展開中に打ち切る）が起きていない |

### 不合格（1つでも当たれば直っていない）

| # | 症状 | 何を意味するか |
|---|---|---|
| **B1** | `stalled` が出る | **打ち切りが残っている。** `disk_bytes` と `disk_idle_s` の値で、どちらの信号が死んでいたかを読む |
| **B2** | `disk_bytes=0` のまま進む | **観測点が違う**（サンドボックス内の `temporaryDirectory` を見ていない） |
| **B3** | 取得完了後、展開中に `stalled` | **欠陥2が残っている。** `snapshotIsComplete` が真を返していない |
| **B4** | 取得が**完了してしまい 65秒に届かない** | **事故を再現できていない。** 合格でも不合格でもない ── **判定不能として記録する** |

> **B4 を「合格」と書かないこと。** キャッシュが効いて速く終われば、**この検証は何も測っていない。**
> その場合は**取得済みのスナップショットを退けてやり直す**か、**判定不能のまま残す。**

## 判定

| # | 条件 | 結果 |
|---|---|---|
| **A1** | 65秒を越えて取得が続く | **合格。** **448秒**継続（事故は65秒で打ち切られた） |
| **A2** | `stalled` が出ない | **合格。** 0件 |
| **A3** | ログに `disk_bytes=` が0でない値で出る | **⚠ 測れていない** |
| **A4** | `disk_bytes` が単調に増える | **⚠ ログ経由では測れていない**（`du` では単調増加を確認） |
| **A5** | 完了して展開へ進む | 未（取得継続中） |

### ⚠ **A3 が測れていないことの意味 —— 「直った」と書けない**

**`[LOAD] event=tick` は `SOPHIA_LOG_LOAD=1` のときだけ出る。** `make app-watch` はこれを設定しない。
**したがって `disk_bytes=` の値がログに1行も無い。**

> **打ち切られなかったことは確かだが、「ディスク信号が打ち切りを止めた」ことは示せていない。**
> **今回の走行で `Progress` が正常に更新されていただけ**という可能性が残る
> （事故は `Progress` が 14MB で凍った状況だった。**その状況の再現を確認していない**）。

**言えるのは「退行していないこと」と「事故の65倍以上の時間、健全に続いていること」まで。**
**`SOPHIA_LOG_LOAD=1` で取り直すこと** ── それで `disk_bytes` と `progress` の両方が
1行に並び、**どちらの信号が生きていたかが分かる。**

### 条件として添える

- **一時ディレクトリに 7.5G の残骸が在る状態で走らせた。** 観測関数は `modified >= startedAt` で
  除くので判定は汚れないが、**除いていることと、除く必要があったことの両方が条件である**
- **スワップ 10.3GB 使用・空き 72MB** ── 今朝「実測を凍結した」ときとほぼ同じ圧迫下である。
  **合否（打ち切るか否か）は正しさの話なので影響を受けないが、65秒という閾値は時間の話である。**
  **「届いてしまった」場合に回線由来か圧迫由来かを分けられない**（検証役の指摘）

### これが「ディスク信号が効いている」ことの直接の証拠である

**`completed_bytes` は 14,275,517 から1バイトも動いていない**（Issue #48 の再現）。

**`idle_s` は 70秒を越えているのに `stalled` にならない** ── **ディスク側が時計を戻し続けているからである。**

> **1回目は「打ち切られなかった」しか言えなかった。**
> **2回目は「なぜ打ち切られなかったか」が1行に並んでいる。**
> **`SOPHIA_LOG_LOAD=1` を既定にした意味がこれである。**

### 速度について

1回目の終盤は **0.42 MB/s** まで落ちた。**古いアプリと新しいビルドが同時に走っていたため。**

# 3回目 ── **99.2% で落ちた。そして完走は「手で組み立てて」到達した**

## 何が起きたか

**2回目の走行は 23:06 に止まった。打ち切りではない。**

```
一時ファイル   4,571,486,285 bytes で停止（23:06:02）
実ファイル     4,607,835,174 bytes（HuggingFace の x-linked-size）
差             36,348,889 bytes ＝ **99.2% で落ちた**
stalled        0件（見張りは打ち切っていない）
[LOAD] 行      23:06 で完全に途絶 ＝ **見張りのタスクごと終了 ＝ `load()` が戻った**
アプリ         CPU 0.0% / RSS 40MB / 接続0本 / 一時ファイルを開いてすらいない
```

**つまり `downloadSnapshot` が最後の36MBを残して失敗し、4.57GB が孤児になった。**

> **これが一時ディレクトリに 46件・7.5GB が積み上がっていた本当の理由である。**
> **やり直すたびに 4.5GB を捨てている。** swift-huggingface 0.9.0 に**再開の仕組みが無い。**

**⚠ 失敗の理由はアプリ側にもOSのログにも残っていない。** `[LOAD]` は最後まで
`event=idle` を出し続け、エラー行を1つも残さずに途絶した。**「なぜ終わったか」が
どこにも記録されていない**のは、今回いちばん困った点である。

## 完走のさせ方（**回避策であって、直しではない**）

**孤児になった 4.57GB を土台にして、残り36MBだけを `curl -C -` で継ぎ足した。**

```
$ curl -sL -C - -o <blobs>/f2d296… <model.safetensors の URL>
http=206 dl=36348889 time=5.4

$ shasum -a 256 <blob>
f2d29621aab300336ad645567ff38c42aac755513006ef4e8a579cf7ef5256d8   ← x-linked-etag と一致
```

**先頭 4.57GB は無傷だった**（CFNetwork は順に書くので、部分ファイルは正しい前置である）。

**HuggingFace のキャッシュ構造に合わせて置いた:**
```
blobs/f2d296…（4,607,835,174 bytes）
snapshots/545dc4…/model.safetensors -> ../../blobs/f2d296…
```

**結果:**
```
[MEM] stage=load_end model=mlx-community/Qwen3-8B-4bit active_mb=4394.3 peak_mb=4394.3
```
**モデルが載った。36MB の転送で済んだ**（4.6GB を落とし直さずに）。

## ⚠ 残っている欠陥 ── **これは直っていない**

| | |
|---|---|
| **症状** | 取得が終盤で失敗すると、**部分ファイルが孤児になり、次の試行はゼロから始まる** |
| **規模** | 46件・7.5GB の残骸。**1回の失敗で最大4.5GBを捨てる** |
| **なぜ致命的か** | 16GB機・遅い回線では、**成功確率が低いほど失敗が積み上がる。** 今回は3回試して3回とも終盤で落ちた |
| **原因** | swift-huggingface 0.9.0 の `downloadSnapshot` に**再開が無い。** 失敗理由も伝わってこない |
| **手当ての方向** | ① 部分ファイルを残して次回 `Range` で再開する ② 失敗理由をログに残す ③ 打ち切り時に自分の部分ファイルを片付ける |

> **今回の停止検知の直しは「誤って打ち切ること」を止めた。**
> **「落ちたときに全部捨てること」は別の欠陥であり、まだ在る。**
