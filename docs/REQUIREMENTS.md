## 1. 背景と目的

### 1.1 背景

生成AIを業務で使う際、入力内容が外部サービスへ送信されることが制約になる場面がある。
社内文書・顧客情報・未公開のソースコードなどは、外部APIに投げる判断がしにくい。

一方、Apple Silicon の性能向上により、7〜8B規模のモデルであれば
ローカルマシン単体で実用的な速度で動作するようになっている。

### 1.2 目的

> **独自モデルを内蔵した、ローカル完結のデスクトップAI。会話は端末の外に出ない。**

これが到達目標であり、以下の要件はすべてこの一文を分解したものである。
本プロジェクトは**2つの目的**を持ち、両者は独立して進行する。

**目的A: 一人に合わせて調整できるデスクトップAIアプリを作る。**
最終的には**開発者本人以外も利用できる単体アプリ**として配布する。

> **⚠ 2026-08-23 訂正。** 旧文は「**Claudeデスクトップアプリのような使用感**を、
> ローカルモデルで実現する」だった。**これは撤回する。**
> **汎用アシスタントの使用感は1億人に向けて最適化されたものであり、その大半は
> 「知らない相手に対する保険料」である**（安全側の但し書き・一般論の前置き・断定の回避）。
> **相手が一人だと分かっていれば、その保険料は払わなくてよい。**
> 真似るべき対象ではない ── 詳細は [PHILOSOPHY.md](PHILOSOPHY.md)。

**目的B: その人のための重みを作る。**
既存モデルを利用するだけでなく、**新しい重みを持つモデルそのものを開発する**。
**追うのは汎用の賢さではなく、「その人を知っている」状態を重みに持たせることである。**
ローカルで着手し、**性能を段階的に上げ、上限に達した時点でクラウドへ移行する**
（**学習のみ。推論はローカルを維持する**）。

両者の接点は「モデルファイル1個」のみ。アプリはそれを読むだけの構造とし、
どちらかの完成をもう一方が待たない設計とする（[DESIGN.md](DESIGN.md) 第4章）。

### 1.3 達成したい状態

- 機密性のある文章の作成・推敲を、外部送信なしに行える
- コードの相談を、社外に出せないソースコードに対しても行える
- 利用者が Ollama や Python などを個別に導入することなく、アプリを入れるだけで使える
- **自分のデータで鍛えた、自分だけのモデルがアプリの中で動いている**

## 2. スコープ

### 2.1 対象

**目的A（アプリ）**

- macOS（Apple Silicon）向けデスクトップアプリケーション
- ローカルでのテキスト生成（チャット・文章作成・コーディング支援）
- モデルの取得・管理・切替
- 会話履歴の保存と再開

**目的B（モデル）**

- モデルマージによる新しい重みの生成（ローカル・0円）
- LoRA/QLoRA による微調整とベースへの融合（ローカル・0円）
- 訓練データの設計と整備
- 品質評価基盤の構築
- **上限到達後のクラウドでの学習**（大規模SFT・継続事前学習）

段階と移行条件は [ROADMAP.md](ROADMAP.md) を正とする。

### 2.2 対象外（現時点）

| 項目 | 理由 |
|---|---|
| 画像生成・音声処理 | 用途に含まれない。メモリ制約上も同時実現は困難 |
| RAG（埋め込み＋ベクトル検索による文書付与） | **目的Bの代替にはならない**（モデル自体を作ることが要件）。**ただし「検索そのもの」はスコープ外ではない** ── **2026-08-23、ウェブ検索を FR-30 として一級の要件にした。** 事実を外に置くことは**モデルを小さく保つ手段**であり、目的Bと競合しない。埋め込み方式の RAG（FR-15）を採るかは未決事項#5 のまま |
| スクラッチ事前学習 | 8B級で数千万円規模。組織的投資が必要。ROADMAP の M6 として将来の検討対象に留める |
| チーム利用・サーバ運用 | 単一マシン上の個人利用が前提 |
| Windows / Linux 対応 | 第9章の未決事項。初版は macOS のみ |
| クラウドAPI（Claude/OpenAI等）への**推論**接続 | 「外部に出さない」目的と相反する。**クラウドは学習にのみ使用し、推論はローカルを維持する** |

## 3. 用語

| 用語 | 意味 |
|---|---|
| モデル | テキスト生成を行う学習済みの重み |
| **MLX形式** | **アプリが読む形式。** `config.json` / `*.safetensors` / `tokenizer.json` 一式が入った**ディレクトリ**。単一ファイルではない |
| GGUF | ローカル推論で広く使われる単一ファイル形式。**アプリでは使わない。** MLX は `.safetensors` しか読めない（[DESIGN.md](DESIGN.md) 第7.1節）。`modelfiles/` の Ollama 用資産は開発用スタック専用として残る |
| 量子化 | 重みを低精度化してサイズと必要メモリを減らす手法。Ollama 側は Q4_K_M、MLX 側は 4bit（**方式が違うため品質が同じとは限らない。未計測**） |
| 推論エンジン | モデルを読み込み、トークンを生成する実行基盤 |
| コンテキスト長 | モデルが一度に扱えるトークン数。会話が長くなると古い部分が切り捨てられる |
| TTFT | Time To First Token。入力してから最初の文字が出るまでの時間 |
| 公証 | Apple による配布アプリの検証。未実施だと利用者側で警告が出る |

## 4. 前提条件と制約

### 4.1 開発環境の制約

| 項目 | 値 | 影響 |
|---|---|---|
| 開発機 | MacBook Air M3 / 16GB / **ファンレス** | 実質9〜10GBがモデル用の上限。7〜8Bが常用、14Bが限界 |
| 熱設計 | ファンなし | 長時間の連続生成で性能が2〜3割低下する |
| メモリ形態 | ユニファイドメモリ | Ollama サーバ・Open WebUI・Docker 等の常駐がそのままモデル用メモリを削る |

このため、**開発機で快適に動く構成が、そのまま最低動作環境の指標になる**。

> **アプリと開発用スタックは同時に動かせない。** アプリ側の常駐見積りは
> 重み4.6GB + KV等で約5.4GB（[DESIGN.md](DESIGN.md) 7.4節。**合計は未確認**）であり、
> ここに Ollama を並べると16GB機では計測も実利用も壊れる。

### 4.2 配布上の制約

- 配布には Apple Developer Program（年額 $99）が必要。**加入済み**（[DESIGN.md](DESIGN.md) 第11章）。
  未加入だと利用者側で「開発元を確認できません」の警告が出て実用に耐えない、という制約自体は残る
- **Metal シェーダのバンドル（`mlx-swift_Cmlx.bundle`）が署名・公証の対象に含まれる。**
  これは Xcode ビルドでのみ生成される（`swift build` では作られない）。
  Electron 版で問題だった `.node` ネイティブアドオンは存在しなくなったが、
  **この経路で公証を通した実績が無い**ため、A2 で空アプリを1度通して確かめる
  （[DESIGN.md](DESIGN.md) 11.3節 / 第12章 リスク1）

### 4.3 環境上の制約

- ポート割り当ては開発機の環境台帳を正とする。開発用の Ollama は 11434、
  参照UI（Open WebUI）は 8081。8080 は他プロジェクトが使用中
- **アプリ自身はポートを使わない。** 上記は計測基盤（A0の資産）と参照UIのものである。
  MLX は常駐サーバを持たず、アプリのプロセス内で推論する

| ID | 要件 | 優先 |
|---|---|:--:|
| FR-01 | 利用者の入力に対し、モデルの応答を**トークンが確定するたびに逐次表示**する | A |
| FR-02 | 生成中の応答を利用者が**中断**できる | A |
| FR-03 | 会話を保存し、一覧から選んで**再開**できる | A |
| FR-04 | 会話を削除できる。削除は取り消せない旨を提示する | A |
| FR-05 | 用途別の**役割（システムプロンプト）を切り替え**られる（文章作成 / コーディング等） | A |
| FR-06 | 応答内のコードブロックを**シンタックスハイライト表示**し、コピーできる | A |
| FR-07 | 初回起動時に**モデルを取得**する。進捗・残量・中断・再開に対応する | A |
| FR-08 | 搭載メモリ量から**推奨モデルを提示**する（16GB→7〜8B、32GB以上→14B以上） | A |
| FR-09 | 導入済みモデルの**一覧・切替・削除**ができる | A |
| FR-10 | 生成パラメータ（temperature、コンテキスト長 等）を設定画面から変更できる | A |
| FR-11 | モデルの読込・生成に失敗した場合、原因と対処を**日本語で提示**する | A |
| FR-12 | 会話を Markdown 形式で書き出せる | B |
| FR-13 | 会話履歴を全文検索できる | B |
| FR-14 | 応答速度（TTFT / tok/s）と**入力トークン数**を利用者が確認できる | **A** |
| FR-15 | ローカルの文書ファイルを読み込ませて質問できる（RAG） | C |
| FR-16 | アプリの自動更新 | C |
| FR-17 | 思考モード対応モデルでは、**思考テキストを本文と分けて表示**する（折りたたみ可能） | A |
| FR-18 | 思考モードを会話ごとにON/OFFできる。有効時は生成トークン上限を自動的に引き上げる | A |
| FR-19 | **ローカルのファイル・ディレクトリを参照できる**（読み取り系ツール） | B |
| FR-20 | **ローカル環境を操作できる**（ファイル書き込み・コマンド実行）。**変更系の実行前に利用者の承認を必須とする** | B |
| FR-21 | ツール定義は**必要時のみ注入**する。常時注入をしない（クライアント起因のプロンプト肥大を設計で禁止） | B |
| FR-22 | すべてのツール実行を監査ログとして記録し、後から参照できる | B |
| FR-23 | モデルが**自分を Sophia として認識**し、名乗る。基盤モデルについて偽らない | A |
| FR-24 | 初回に、**少数の質問**で利用者像の初期値を作る。**質問の回数に上限を持つ。**中断・スキップでき、後から再開できる | B |
| FR-25 | 利用者像を**内容**（陳腐化する事実）と**様式**（蓄積する振る舞い）に分けて保持し、**更新方針と保管先の両方を変える。既定では、どちらも毎ターンのプロンプトに載せない** | B |
| FR-26 | **様式は直接質問しない。** 同じ問いへの複数の回答案から**選ばせて**採取する | B |
| FR-27 | 利用者の**訂正**をその場で記録し、**まとめて利用者像へ反映**できる。反映に要する時間と、**その間アプリが使えるかを事前に示し、中断できる** | B |

| FR-29 | 利用者像の費用を利用者が確認できる ─ **毎ターン消費しているトークン数**（**既定は 0**）と、**反映に一度払った時間**（FR-14 の延長） | B |

| FR-31 | 利用者の訂正を記録するとき、**ずれの向き**（踏み込みすぎ / 逃げすぎ）を併せて記録する。**向きの無い訂正は、焼き込むと平均化されて何も学ばない** | B |

> **FR-30・FR-31 と NFR-01 の改定は 2026-08-23、利用者の決定である。**
>
> **NFR-01 は「外部へ出さない」という約束を捨てたのではなく、出るものを2つに限って明示した。**
> 理由は費用の計算が片側しか数えていなかったことにある ──
> **検索の費用（定義 +約100 / 結果 +約183）は数えていたが、検索しない費用を数えていなかった。**
> 4bit 量子化の 8B は知らないことを断言するので、訂正の往復が3〜4回増える。
> **往復のたびに会話は先頭から再プリフィルされ（実測21秒）、間違った答えは履歴に残って落とせない。**
> **検索結果は栞にして落とせるが、モデルが自分で書いた誤りは会話の一部なので落とせない。**
> **測るべきは「1ターンの費用」ではなく「正しい答えに辿り着くまでの総費用」だった。**
>
> **FR-31 の背景（設計の起点に関わる）。** VISION の仮説は「少ないエネルギーで会話が成り立つ鍵は
> パーソナライズである」であって、**世界の事実を全部モデルに詰め込むこと（＝「神を作る」）ではない。**
> したがって置き場所は分かれる ── **事実は外に置いて要るときだけ取る（FR-30）／その人のことは重みに焼く（第14章）。**
>
> **そして調整すべきものは「好み」ではなく「確信の表明の仕方」である。**
> 嘘をつけば一度で信用を失い、逃げれば正しくても使えない。**どちらも「バカに見える」。**
> **その匙加減は一人に対してしか最適化できない** ── 1億人に向けると、
> 誰も怒らせない代わりに誰にも刺さらない言い方へ収束する。
> **汎用モデルが払っている費用の大半は、知らない相手に対する保険である。**
> **相手が一人だと分かっていれば、その保険料は返せる。トークンでも、エネルギーでも。**
> **FR-30 はここに効く** ── 根拠が無いまま「嘘をつくな」と言えば、モデルは逃げるしかない。
> **検索は、断言してよい根拠を取りに行く仕組みである。だから結果は出典を伴わなければならない。**

> FR-19〜22 は 2026-08-16 追加。「チャットだけでなく、ローカル環境を参照・操作できる
> エージェントにする」という要望による。フェーズA2 の中心スコープ。
> FR-21 が要件になっているのは、ツール定義32個の常時注入（4,550トークン）が
> 応答を34秒にしていた実測（TUNING.md 第2章）を反面教師とするため。
> FR-20 の承認必須は、ファイル内容経由のプロンプトインジェクションが
> あっても変更系が人間の承認を通らずに実行されない、という安全設計を兼ねる。
>
> **FR-19〜22 の設計はまだ存在しない。** [DESIGN.md](DESIGN.md) にツール実行層の章が無い
> （同 13.1節に A2 の作業項目として立ててある）。要件だけが先行している状態である。

> **FR-23 は 2026-08-17 追加。** A1 で実装済み（アプリの system 発言として毎ターン先頭に置く。
> [DESIGN.md](DESIGN.md) 4.8節に設計と費用の判断）。
> **素の Qwen3 は「Sophia」を知らない。** この人格はこちらが与えない限り存在しない
> （素の状態で何と名乗るかは**実機で未確認**）。
> 「独自モデルを内蔵したデスクトップAI」（1.2節）を名乗る以上、名前は要件である。
> 一方で、基盤がオープンモデルであることを偽らせない条件を同時に置いている。
> **恒久的にプロンプトで払い続けるものではない。** 最終的には重みへ移す

> **狙いは「親しみ」ではなく、送るトークンを減らすことである。**
> VISION の第1因子（そもそも無駄を送らない / 10〜20倍）は、
> **相手を知っていれば説明しなくて済む**ことで成立する。
> 行動ログだけで事前分布を作ると数週間かかり、その間ずっと誤読に付き合わせる。
> **質問はその数週間を数分に圧縮する試みである** ─ うまい質問1つは、
> 自然な会話の何十往復ぶんもの信号を運ぶ。
>
> ### 2026-08-18 の書き直し ─ **「毎ターン注入」という前提を撤回した**
>
> 初版の FR-24〜29 は、**採った利用者像を毎ターン system プロンプトへ載せる**前提で書かれていた。
> **同日の実測がその前提を壊した**（[DESIGN.md](DESIGN.md) 14.0節）。
>
> | 実測（2026-08-18 / 開発機 M3・16GB / Qwen3-8B-4bit） | 値 |
> |---|--:|
> | 入力予算 1,000 のうち、**利用者の発言に残る分** | **33 トークン**（日本語で約45字） |
> | 実際に投げていた入力（予算の1.7倍。**止まらず、遅くなっただけ**） | **1,730 / 1,764 トークン** |
> | そのときのプリフィル | **20.32 / 21.50 秒** |
>
> **「入らない」のではなく「会話が続く限り払い続ける」ことが問題である。**
> 500トークンの利用者像は 1,000ターンで 500,000トークンになる。
>
> **したがって FR-25 は保管先まで規定する。** 既定は**貯めるが送らない**。
> 効かせる先は**その人専用の翻訳層（入力側の小さいモデル）とその重み**であり、
> **本体が毎ターン払う利用者像の費用は 0 である**（[DESIGN.md](DESIGN.md) 14.3〜14.7節）。
> **FR-29 の「既定は 0」はこの帰結であって、努力目標ではない。**
>
> **FR-26 が独立した要件になっている理由。** 人は自分の様式を正しく申告できない。
> 「説明はどのくらい詳しいのが良いか」と訊くと、実際の好みではなく**理想の自分**が返る。
> 内容（事実）は自己申告が正確だが、様式（振る舞い）は選択させてしか採れない。
> **これは実装の都合ではなく、取れるデータの性質の問題**なので要件に置く。
>
> **FR-24 が回数の上限を持つ理由。** **訊くこと自体が利用者のエネルギーである。**
> トークンに予算表を置いたのと同じ理由で、質問にも予算を置く
> （[DESIGN.md](DESIGN.md) 14.9節）。
>
> **FR-27 が「事前に示し、中断できる」を含む理由。** 重みへ反映するには学習が要り、
> **学習中は同じモデルでチャットできない**（ライブラリの形からそう決まる。
> [DESIGN.md](DESIGN.md) 14.11節②）。**使えない時間が予告なく来るのは障害と区別がつかない。**
>
> **FR-28 が「反映前へ戻せる」を含む理由。** **誤った利用者像は誤読を強化する。**
> 重みへ焼き込んだものは外から見えない（[VISION.md](VISION.md)「リスク」）。
> **逃げ道はあれば良い機能ではなく、必須である。**
> 同じ理由で「翻訳された指示を確認できる」を置いている ──
> **答えが外れたとき、本体のせいか翻訳のせいかを切り分けられないと、
> 利用者は「モデルが馬鹿だ」に飛ぶ**（[DESIGN.md](DESIGN.md) 14.5節）。
>
> **FR-29 が要る理由。** 利用者像はプロンプトに載せると**毎ターン課金される。**
> **前置きだけで毎ターン 105トークン**を払っている（実測 2026-08-18。
> **自己認識＋チャットテンプレートの固定分＋ごく短い user ターンの合計であり、
> 自己認識単独の値は分離して測っていない** ─ `ChatOptions.swift` の但し書き）。
> 置き換える文脈より高くつけば、**第1因子を実現するはずの機構が別の形の常時注入になる。**
> Open WebUI がツール定義4,550トークンを毎回送っていたのと構造は同じである（TUNING.md 第2章）。
> **費用が見えない限り、この失敗は必ず起きる。**
>
> **FR-05 の「プロファイル」とは別物である。** FR-05（`profiles` テーブル）は
> **アシスタント側の役割**（相談相手 / コード書き）であり、FR-24〜29 は**利用者側の像**である。
> 名前が紛らわしいので、本書と DESIGN では後者を一貫して**「利用者像」**と呼ぶ。
>
> > **NFR-12（何を根拠にしたか辿れる）との緊張。** 重みへ焼いたものは、
> > 推論時には根拠として提示できない。**満たしているのは重みではなく DB のほうである** ──
> > 焼き込んだ後も、言語化された文を `user_traits` に残す
> > （**重みは記録ではなく複製である**。[DESIGN.md](DESIGN.md) 14.11節④・14.14節）。

> **FR-01 の読み替え。** 1トークン = 1チャンクではない。デトークナイザが Unicode 境界で
> 出力を保留するため、チャンクが出ない回もまとめて出る回もある
> （[DESIGN.md](DESIGN.md) 5.2節）。受入判定は「トークンが確定するたびに逐次届き、
> 文字化けした断片が画面に出ないこと」で行う。
>
> **FR-14 を B から A へ上げた理由。** 「気づいたら5,000トークン送っていた」を
> 構造的に起こさないための唯一の手段が、入力トークン数の常時表示である
> （[DESIGN.md](DESIGN.md) 2.2節 / VISION 第1因子）。初版後に足す性質のものではない。
> A1 で実装済み。

## 6. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | プライバシー | **会話本文・履歴・ファイルの中身・利用者像を外部へ送信しない。** 外部へ出てよいのは **(a) モデルの取得と更新確認 (b) 利用者が検索を有効にした会話における、モデルが組み立てた検索語** の2つに限る。**(b) では送信するものを送信前に画面へ表示し、監査ログへ記録する**（2026-08-23 改定。旧文は「通信はモデル取得と更新確認に限定」だった） |

| NFR-03b | 性能（生成速度） | 冷間で 13 tok/s 以上、**連続使用時（熱制限下）で 7 tok/s 以上**。実測の基準値は `BENCH_RESULTS.md` |

| NFR-05 | 配布性 | 利用者が**アプリ以外を導入せずに使える**こと。Ollama・Python・Homebrew等への依存を残さない |
| NFR-06 | 配布サイズ | アプリ本体は 300MB 以内。モデルは本体に同梱せず初回取得とする |
| NFR-07 | 対応環境 | macOS 14 以降 / Apple Silicon。初版は arm64 のみ |
| NFR-08 | 完全性 | 取得したモデルは sha256 で検証する。破損時は再取得を促す |
| NFR-09 | 保守性 | 推論エンジンを差し替え可能な形で抽象化する（理由は下記の3点。**v1.0 の「開発時と配布時で実装が異なるため」は消滅した**） |
| NFR-10 | 復旧性 | モデル取得の中断・容量不足・ネットワーク断から復帰できる |

> **NFR-03 の「約170トークン」の出所。** プリフィルは最短の実測点でも273トークンで1.6秒
> かかっている（[DESIGN.md](DESIGN.md) 第2章）。ここから内挿すると1秒に収まるのは約170トークン。
> **これは Ollama + GGUF での実測から出した値である。**
>
> **⚠️ アプリ（MLX）の実測2点は、この170という数字にも、NFR-03 の達成にも疑いを投げている。**
>
> - **1往復目**: 入力**104トークンで TTFT 0.97秒** ─ すでに1秒の上限に達している。
>   **閾値は170より相当低い可能性がある。**
> - **2往復目**: 入力156トークンで **TTFT 11.87秒。NFR-03 は破れている。**
>   プリフィルだけが9.2倍崩れており（デコードは無傷）、原因は未特定
>   （[DESIGN.md](DESIGN.md) 2.6節・リスク21）。
>
> **「初回だけ1秒以内」は、要件を満たしていないのと同じである。**
> ただし Debug ビルド（デバッガは非接続）の2点なので、**Release で取り直すまで
> 閾値そのものは書き換えないこと。** 下方修正するにせよ、根拠が2点では足りない。
> **先に決着させるべきはプリフィル崩れの原因のほうである。**
>
> なお system プロンプト（FR-23）が毎ターン概算+97トークンを先に消費する。
> 上の104トークンにもこれが含まれており、**利用者の入力は実質30トークン程度で
> 予算を使い切っていた**ことになる。`SOPHIA_SYSTEM_PROMPT=0` で切れば
> 素の性能を測り続けられる（[DESIGN.md](DESIGN.md) 4.8節）。

> **NFR-09 を残す理由（3点）。** MLX は開発時も配布時も同じ実装なので、v1.0 の理由は消えた。
> それでも抽象化は要る（[DESIGN.md](DESIGN.md) 第1章 原則1）。
> 1. **トラックBの成果物へ載せ替える。** モデルが変わればトークナイザ・思考プロトコル・
>    推奨パラメータが変わる
> 2. **モデルの規模を使い分ける。**「こんにちは」に8Bを使わない（VISION 第2因子）
> 3. **解剖版のエンジンと素の実装を並べて A/B する。** 差し替えられないと比較が取れない

## 7. 受入条件

初版（**フェーズ A4 完了時点**）を完成と判断する条件。
どの条件をどのフェーズで満たすかは [DESIGN.md](DESIGN.md) 第13章が正
（条件2〜7 が A3、条件1 が A4）。

1. Ollama をインストールしていないMacに `.dmg` を導入し、警告なく起動できる
2. 初回起動でモデルを取得し、そのまま会話できる
3. 会話中に機内モード（ネットワーク遮断）にしても、生成が継続する
4. **入力予算（約1,000トークン／日本語で約2,000字）を超える長文を貼り付けたとき、
   警告が出たうえで指示が無視されずに応答が返る**
5. 生成中にウィンドウのスクロールと中断操作が効く
6. アプリを再起動しても会話履歴が残っている
7. モデルの取得を途中で切断し、再開できる
8. 開発機で NFR-03 の速度を満たす（入力長の前提込みで判定する）

> **条件4 を書き換えた理由。** v1.0 は「5,000字程度」としていたが、これは約2,500トークンで
> 設計値の入力予算1,000トークンの2.5倍にあたり、**要件どうしが正面から矛盾していた**
> （[DESIGN.md](DESIGN.md) 2.2節）。長文を黙って受けるのではなく、
> **超過を隠さず見せたうえで応答する**のが設計判断である（VISION 第1因子）。

> | **Xserver 等のレンタルサーバ** | **定額。使われても増えない** | プランの容量まで | **無い** | **完全に自分** |
>
> **費用構造が2種類あることに注意。** HuggingFace / GitHub は無料、Firebase は**従量**、
> レンタルサーバは**定額**。**従量だけが「使われるほど増える」** ─
> 無料で配るアプリの取得元としては、ここが唯一の不安要素になる。
> **既にレンタルサーバを契約しているなら、追加コストゼロで従量の不安が消える**という利点がある。
> 代償は **CDN が無い**ことで、海外からの取得が遅くなる（国内利用が前提なら影響は小さい）。
>
> **アプリ側はどれを選んでも変わらない** ─ 素の HTTPS で URL を叩くだけである。
> **自前ダウンローダを書くなら、取得元を設定で差し替えられる形にしておくこと。**
> そうすれば、この決定を最後まで遅らせられる。
>
> **転送料が効くのは規模のせいである。** 4.6GB を1人が落とすたび約 $0.55 ─
> 1,000インストールで約 $550。**無料で配るアプリのベースモデル置き場としては成立しない。**
> 一方 **0.6B（約340MB）なら約 $0.04/人**で、桁が変わる。
>
> **したがって役割で分けるのが素直:**
> - **ベースの 8B（他人のモデル）** → **HuggingFace のまま。** 既に公開されているものを
>   自分でミラーして転送料を払う理由が薄い
> - **独自モデル（トラックBの成果物・小さい）** → **自分の置き場。**
>   第2因子と蒸留が向かう先は小さいモデルなので、GitHub Releases の 2GB にも収まる見込み
>
> **2026-08-18、Firebase プロジェクトを作成した**（プロジェクトID `sophia-bfe97` /
> 組織 `xerographix.co.jp`）。**独自モデルの置き場として確保したものであり、
> ベースモデルの取得元を移す決定ではない。**
>
> **⚠️ ただし、当面この決定は不要である。**
> **利用者が本人1人のあいだは、取得元そのものが要らない。**
> 独自モデルは手元にあるので、[DESIGN.md](DESIGN.md) 第7章の**経路C
> （ローカルディレクトリ読み込み）**で足りる。ダウンロードも公開範囲も転送料も発生しない。
> **取得元が要るのは「他人に配るとき」＝ A4 からである。**
> それまでバケツは空のまま置いておけばよい。
>
> > **⚠️ 公開バケツは従量課金である。** 公開読み取りにすると誰でも何度でも落とせる。
> > **予算アラートを先に置くこと。** これは一般的な事故であって、想定の話ではない。
>
> **⚠️ Firebase SDK は入れないこと。** 公開URL か署名付きURL へ素の HTTPS で取りに行く。
> 理由は2つ ─ **①依存が増える**（`mlx-swift_Cmlx.bundle` で既に公証の懸念がある。第12章 リスク1）、
> **②思想と衝突する**（Firebase SDK は既定で解析を持ち込む。
> **NFR-01「会話は端末の外に出ない」を掲げるアプリが Google の計測基盤を同梱するのは筋が悪い**）。
> **バケツに置いてURLで取るだけなら依存はゼロ**であり、自前ダウンローダとも相性が良い。
