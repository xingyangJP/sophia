## 0. 記法 — 確認できた事実と未確認の推測を分ける

本書の記述には必ず次のいずれかの印を付ける。**印のない断定は書かない。**

| 印 | 意味 |
|---|---|
| **【実測】** | 2026-08-16 に開発機（MacBook Air M3 / macOS 26.5.2 / Build 25F84）で実行して得た値。再現方法を併記する |
| **【出典】** | Apple の公開ドキュメント、または Sophia の実装コードに記載がある。参照先（ファイル名）を併記する |
| **【計算】** | 実測値から数式で導いた値。コントラスト比は WCAG 2.1 の sRGB 相対輝度の定義に従う。**目視の印象ではない** |
| **【推測】** | 根拠はあるが本環境で確認していない。**実装時に検証すること** |
| **【未確認】** | 調べたが確定できなかった。作業項目として残す |

### 0.1 検証環境

| 項目 | 値 |
|---|---|
| OS | macOS 26.5.2（Build 25F84）/ MacBook Air M3 16GB |
| 表示 | Retina（`devicePixelRatio = 2`）【実測】 |
| システム外観 | ライト（`AppleInterfaceStyle` 未設定）【実測】 |
| 実装 | SwiftUI + AppKit（`Sophia/Sources/UI/`、`Sophia/Sources/Shared/DesignTokens.swift`） |

**OS のメジャーを上げたら本書の【実測】は取り直すこと。**
特に第5章の寸法と第2.6節のウィンドウ角丸は OS バージョンに紐づいた値である。

### 0.2 検証方法

- AppKit の値: Swift スクリプトで `NSFont` / `NSWindow` / `NSColor` / `NSSplitViewItem` を直接読む
- コントラスト比: WCAG 2.1 の sRGB 相対輝度の定義に従って計算（アルファ付きは地に合成した実効色で算出）

**視覚的な確認（材質が実際にどう見えるか）は行えていない。**
本書の執筆環境ではスクリーンキャプチャの権限がなく、画面を撮れなかった。
第2章の「見え方」に関する記述はすべて【推測】であり、目視確認は第9章のチェックリストに残してある。

## 1. 全体方針 — 何を OS に任せ、何を自分で描くか

| 要素 | 担当 | 理由 |
|---|---|---|
| ウィンドウの角丸・影 | **OS** | 半径は OS バージョンで変わる。macOS 26 の実測値は 16pt（2.6節）。固定値で描くと次の OS で古く見える |
| 背景の透過・ブラー | **OS** | サイドバーは `NavigationSplitView` が材質を持っている。**塗らなければ透ける**（4.5節） |
| トラフィックライト | **OS** | 描画・ホバー・無効状態・フルスクリーン遷移すべて OS が持っている。**座標も OS が決める**（2.3節） |
| ウィンドウのドラッグ | **OS** | ツールバー領域は最初からドラッグできる。ドラッグ領域の指定は存在しない |
| アプリケーションメニュー | **OS**（`.commands`） | 編集メニューは SwiftUI が既定で持つ（6.1節） |
| ダイアログ | **OS**（`.confirmationDialog`） | シート表示・ボタン配置・キーボード操作が無料で付いてくる |
| フォント | **OS**（`Font.system`） | SF は非公開フォントで名前では呼べない。日本語のフォールバックも AppKit が持つ（3.1節） |
| 日本語入力（変換） | **OS**（`NSTextView`） | 変換中かどうかは AppKit にしかない情報。SwiftUI からは取れない（第8章） |
| 余白・行の高さ・角丸（部品） | **自分** | ただし AppKit の実測値に合わせる（第5章） |
| 配色 | **自分**（Sophia の色） | ここが個性。ただし明暗の反転規則は macOS に合わせる（第4章） |

## 2. ウィンドウの質感

### 2.1 Electron でやっていたことは、ほぼ全部なくなった

**この表が版 1.0 からの最大の差分である。**
実装側にも同じ表が `Sophia/Sources/App/RootView.swift` のコメントとして置いてある【出典: 実装】。

| Electron でやっていたこと | SwiftUI での対応 |
|---|---|
| `vibrancy: 'sidebar'` | `NavigationSplitView` のサイドバーが自前で持つ。**指定不要** |
| `visualEffectState: 'active'` | 相当する指定は無い |
| `backgroundColor: '#00000000'` で透過させる | **逆。塗らなければ透ける。** 不要な `.background` を置かないことが唯一の作法 |
| `titleBarStyle: 'hidden'` + `trafficLightPosition: {19,19}` | `.windowToolbarStyle(.unified)`。**座標指定は不要** |
| `titleBarOverlay` / `env(titlebar-area-x)` | 不要。ツールバーへ入れれば OS が信号機を避ける |
| `app-region: drag` / `no-drag` | 不要。ツールバー領域は最初からドラッグできる |
| `transparent: true` を避ける判断 | そもそも選択肢が無い |
| 1ウィンドウに材質は1つ、という制約 | **制約ごと消えた。** ペインごとに塗る／塗らないを選べる（4.5節） |

**ここから引くべき教訓は「ネイティブでは調整の大半が消える」ことである。**
Electron 時代に費やした労力の多くは、OS がすでに持っているものを CSS で作り直すためのものだった。
新しく UI を足すときも、まず**指定しないで済むか**を疑うこと。

> **【重要】トラフィックライトの座標を自分で計算しないこと。**
> 版 1.0 の第2.3章は `{x: 19, y: 19}` を「Sophia が採る値」として断定していたが、
> ネイティブでは OS の担当である。実装（`SophiaApp.swift`）も座標を持っていない。

### 2.3 タイトルバーとトラフィックライトの実測値

**座標として使う値ではない**（2.1節）。**寸法の基準**として使う。
ヘッダの高さを 52pt と決めているのは、この実測に合わせるためである。

macOS 26.5.2 の純正ウィンドウを AppKit で実測した値【実測: Swift / `standardWindowButton`】:

| ウィンドウの型 | ボタン領域の高さ | 左からの x | 上からの y | ボタンの大きさ |
|---|--:|--:|--:|---|
| 標準タイトルバー（`.titled`） | 32pt | 9 | 9 | 14×14 |
| ツールバー `unified`（Notes / Mail 型） | **52pt** | **19** | **19** | 14×14 |
| ツールバー `unifiedCompact` | 40pt | 12 | 13 | 14×14 |
| ツールバー `expanded` | 48pt | 9 | 9 | 14×14 |

ボタンの原点間隔は **23pt**（=14 + 隙間9）【実測】。3個ぶんの幅は 14×3 + 9×2 = **60pt**。

Sophia は `unified`（52pt）を使う。Notes / Mail と同じリズムになる。
**x=19 / y=19 という値を実装が持つ必要はない** ─ `.unified` を選んだ時点で OS がその位置に置く。

### 2.4 Sophia のウィンドウ設定（SwiftUI）

実装は `Sophia/Sources/App/SophiaApp.swift`【出典: 実装】。
**ウィンドウに関する指定は次の4つしかない。**（版 1.0 の `BrowserWindow` オプションは
タイトルバー・材質・透過・表示遅延まで含めてもっと長かった。差は 2.1 節の表がそのまま説明する）

| 項目 | 値 | 出所 |
|---|--:|---|
| 既定サイズ | 1000 × 700 | 設計判断 |
| 最小サイズ | 640 × 480 | サイドバー240 + 本文の最小400（5.2節） |
| ツールバー | `.unified(showsTitle: false)` | 52pt。2.3節の実測 |
| リサイズ | `.windowResizability(.contentMinSize)` | これを付けないと `.frame(minWidth:)` が効かず内容が潰れる |

数値そのものは `Sophia/Sources/Shared/DesignTokens.swift` の `SophiaMetrics` が単一の出所で、
`SophiaApp` はそこを参照するだけである。**画面ごとに寸法を書かないこと。**

### 2.6 角丸と影 — 自分で描かない

**【実測】macOS 26.5.2 のウィンドウ角丸半径は 16pt。**
（`NSWindow` の非公開プロパティ `_cornerRadius` を KVC で読み取った値。**非公開 API なので保証はない**）

**この値は「知っておく」ためのもので、書くためのものではない。**
Electron 版では独自のマスク（半径 9.0 固定）が OS の 16pt と食い違うという問題を抱えていたが、
**SwiftUI ではウィンドウの角も影も OS が一手に描くので、食い違い自体が起きない。**

**やること・やらないこと:**

- ❌ ルート要素に角丸を掛けて「作る」 → OS の半径と二重になり、四隅に隙間や段差が出る
- ❌ 影を自分で描く → OS の影と二重になる
- ✅ 何も指定しない

## 3. タイポグラフィ

### 3.1 SwiftUI ではフォントの心配がほぼ要らない（Chromium で必要だった対策の顛末）

**版 1.0 の第3.1〜3.4節は、Chromium がシステムフォントを正しく解決できないことへの
対策で埋まっていた。SwiftUI ではその問題が起きない。**

消した対策と、なぜ不要になったかを記録として残す。**これは失敗ではなく、
「レンダラを替えると消える種類の問題だった」という判断材料である。**

| Electron で必要だった対策 | SwiftUI では |
|---|---|
| `-apple-system` は Chromium で解決しない（`BlinkMacSystemFont` が実効）【実測】 | `Font.system(size:)` が `.AppleSystemUIFont` を直接指す。名前解決の問題が存在しない |
| `'SF Pro Text'` / `'SF Mono'` は名前で呼べない【実測】 | 同じ。ただし `Font.system(size:design:.monospaced)` で等幅が取れるので、**名前を書く必要がない** |
| 日本語が `HiraKakuProN-W3` に落ちる（AppKit の `.HiraKakuInterface-W4` より1段細い）【実測】。`@font-face` + `local('HiraginoSans-W4')` で固定していた | **AppKit がフォールバックを持つので、対策なしで W4 側になる**【実測: AppKit 側の解決先が `.HiraKakuInterface-W4` であること】 |
| 等幅の総称に頼ると日本語が Osaka-Mono になる【実測】 | `.monospaced` の日本語フォールバックは**未確認**（下記） |

> **【未確認】Sophia の画面で実際に何のフォントが使われているかは確認していない。**
> 上の表の右列は「AppKit がシステムフォントの日本語に `.HiraKakuInterface-W4` を使う」という
> 2026-08-16 の実測からの帰結であり、**アプリを起動して描画結果を検査したわけではない。**
> 純正アプリと並べた目視確認は第9章に作業として残してある。

**実装は `Sophia/Sources/UI/Theme/SophiaTypography.swift` の `SophiaFont` に閉じている。**
フォント名は1つも書かれていない。これが正しい状態である。

### 3.5 サイズ — AppKit の実測値に合わせる

macOS のテキストスタイルを AppKit から実測した値【実測: `NSFont.preferredFont(forTextStyle:)` と
`NSLayoutManager.defaultLineHeight`】。**pt はそのまま SwiftUI の指定値と 1:1 で対応する**（Retina でも同じ）。

| テキストスタイル | サイズ | 行の高さ | ウェイト | Sophia での用途 | 実装（`SophiaFont`） |
|---|--:|--:|--:|---|---|
| largeTitle | 26 | 32 | regular | 使わない | — |
| title1 | 22 | 26 | regular | 空状態の見出し | `title1` |
| title2 | 17 | 22 | regular | 設定画面の節見出し | `title2` |
| title3 | 15 | 20 | regular | 会話タイトル | `title3` |
| **headline** | **13** | **16** | **semibold (+0.40)** | サイドバーの選択行、ラベル | `headline` |
| **body** | **13** | **16** | regular | **UI 全般の既定** | `body` |
| callout | 12 | 15 | regular | 補助テキスト | `callout` |
| subheadline | 11 | 14 | regular | 日付、メタ情報 | `subhead` |
| footnote | 10 | 13 | regular | 統計表示（FR-14） | `footnote`（等幅数字） |
| caption1 / caption2 | 10 | 13 | regular | 最小の注記 | — |

基準サイズ【実測】: `NSFont.systemFontSize = 13.0` / `smallSystemFontSize = 11.0` / `labelFontSize = 10.0`。

**UI の既定は 13pt / 行の高さ 16pt。** Web の癖で 14pt や 16pt にすると、
それだけで「Mac のアプリではない」という印象になる。

ただし**会話の本文だけは例外**とする。13pt は密度の高い UI 向けの値で、
長文を読ませる領域には小さい。Sophia の本文は **15pt / 行の高さ 24pt** を採る（実装は `SophiaFont.message`）。
【推測】この値は AppKit の実測値ではなく、13pt の UI に対して読みやすさを優先した設計判断である。
実機で読んで調整すること。

> **SwiftUI は行の高さを直接指定できない。**
> 実装は `lineSpacing` の差分で与えている（`SophiaLayout.messageLineSpacing = 6`。
> 24 − 15pt の実測行高 ≒ 18 の差分）。**行高そのものを持つ CSS とは指定の形が違う**ので、
> 上表の「行の高さ」列を実装へ写すときは差分に直すこと。

### 3.6 フォント描画で触ってはいけないもの

- ❌ **文字間（`.tracking()`）の追加**
  SF はサイズごとのトラッキングを内部に持っている。足すと二重にかかる。
- ❌ **`.fontWeight(.ultraLight)` / `.thin`**
  ウェイトは存在するが【実測】、macOS の UI で本文に極細を使う場面はない。

> 版 1.0 にあった `-webkit-font-smoothing: antialiased` の項は削除した。
> CSS プロパティであり、SwiftUI に該当する設定が無い。

## 4. 配色とダークモード

### 4.1 OS の外観に追従する

**実装は `NSColor` の dynamic provider 1つで完結している**【出典: `Sophia/Sources/Shared/DesignTokens.swift`】。

```swift
// 外観ごとに違う値を返す色を作る。SwiftUI の Color 単体では持てない。
NSColor(name: nil) { appearance in
    appearance.bestMatch(from: [.aqua, .darkAqua]) == .darkAqua ? dark : light
}
```

> **`@Environment(\.colorScheme)` で分岐しないこと。**
> 分岐すると、ビューが再評価されない場面で色が取り残される。
> dynamic provider なら描画時に OS が解決するので取り残しが起きない【出典: 実装コメント】。

FR-10 のアプリ内3択（システム / ライト / ダーク）は、`NSApp.appearance` を差し替える形になる見込み。
**A1 では未実装**であり、現状は OS 追従のみ。

#### アクセシビリティ設定への対応【未確認】

macOS には「透明度を下げる」「コントラストを上げる」「視差効果を減らす」がある。
Electron 版は CSS のメディア特性（`prefers-reduced-transparency` 等）で拾っていたが、
**SwiftUI / AppKit 側の等価物を調べ直していない。**
`NSWorkspace.shared.accessibilityDisplayShouldReduceTransparency` などが候補だが、
**A1 時点で一つも実装していない。** 対応は 4.4 節に作業として残す。

### 4.2 AppKit のシステム色

macOS 26.5.2 のシステム色【実測: Swift / `NSAppearance` を切り替えて取得】:

| 色 | ライト（aqua） | ダーク（darkAqua） |
|---|---|---|
| `windowBackgroundColor` | `#FFFFFF` | `#1E1E1E` |
| `underPageBackgroundColor` | `#969696` α0.898 | `#282828` |
| `labelColor` | 黒 α0.847 | 白 α0.847 |
| `secondaryLabelColor` | 黒 α0.498 | 白 α0.549 |
| `tertiaryLabelColor` | 黒 α0.259 | 白 α0.247 |
| `separatorColor` | 黒 α0.098 | 白 α0.098 |
| `controlAccentColor` | `#007AFF` | `#007AFF` |
| `selectedContentBackgroundColor` | `#0064E1` | `#0059D1` |
| `linkColor` | `#0068DA` | `#419CFF` |

**macOS のライトの地は白（`#FFFFFF`）である。** かつての `#ECECEC` ではない。
Sophia のクリーム `#FEF5EB` は白よりわずかに暗く暖かい。**これが Sophia の個性になる。**

**設計上の重要な観察: macOS は文字色を「不透明な色」ではなく「アルファ付きの墨」で定義している。**
ライトは黒 84.7%、ダークは白 84.7%。この方式なら、下に何が来ても（材質の上でも）文字が地に馴染む。
**Sophia もこの方式を踏襲する**（4.3節）。実装の `SophiaColor` も原色 + アルファで書かれている。

#### システムアクセントカラーを使うべきか

**使わない。** Sophia のアクセントはテラコッタ `#D08256` であり、
システムのアクセント（本機では青 `#007AFF`）を混ぜると配色が2系統になって濁る。

ただし例外が2つある:

- **本文中のテキスト選択**は OS の選択色に合わせた方がよい。利用者は他アプリと同じ挙動を期待する。
- **キーボードフォーカスリング**も同様。

【推測】この2点は慣習に基づく判断で、実機比較はしていない。A1 で両方試して決めること。
なお A1 の実装はどちらも SwiftUI の既定に任せており、**明示的な指定を一つも置いていない。**

### 4.3 Sophia のカラートークン設計（本書の中心）

**この節は版 1.0 からまったく変えていない。** WCAG 2.1 の計算値であり、
描画技術に依存しないためである【DESIGN.md 9.3 も同じ扱いをしている】。

#### 設計の骨子 — 役割の入れ替え

DESIGN.md 第9.2章の3色を、ライトとダークで次のように入れ替える。

| 役割 | ライト | ダーク |
|---|---|---|
| **地（広い面）** | クリーム `#FEF5EB` | **チャコールの色相を保った暗色** `#1C1D1F` |
| **墨（文字）** | チャコール `#434548` | **クリーム `#FEF5EB`** |
| **アクセント（細い要素）** | テラコッタ**の濃色版** `#A85426` | テラコッタ **そのまま** `#D08256` |

**入れ替えの要点は3つある。**

1. **クリームとチャコールは、地と墨として役割を丸ごと交換する。**
   ダークでクリームを地にはできない（明るすぎる）が、**墨としてなら使える**。
   クリーム `#FEF5EB` を `#1C1D1F` に載せたときのコントラスト比は **15.64:1**【計算】で、
   純白より柔らかく、暖かさが残る。

2. **チャコール `#434548` をそのままダークの地にはできない。**
   `#434548` の上にクリームを置くと 8.92:1 で読めはするが、
   macOS のダーク地は `#1E1E1E`【実測】であり、`#434548` は明るすぎて
   「浮いたパネル」に見える。**色相（青みのある無彩色、H≒220°）だけを継承した `#1C1D1F` を地にする。**
   ただしチャコールが消えるわけではない。**ダークでは「最も持ち上がった面」として再登場する**
   （`surfaceRaised`）。地 `#1C1D1F` に対する面差は 1.75:1、
   その上に `ink` を載せると 7.86:1 で読める【計算】。
   つまり**チャコールは「墨 → 面」へ、クリームは「地 → 墨」へ役割が移る。**

3. **テラコッタは役割を変えず、明度だけを地と逆方向へ動かす。**
   これが最も見落とされやすい。**テラコッタ `#D08256` はクリームの上ではコントラスト
   2.78:1 しかなく、文字色として使えない**【計算】。
   ライトでは濃色版 `#A85426`（4.92:1）に置き換える必要がある。
   逆にダークの `#1C1D1F` 上では `#D08256` が 5.63:1 で**そのまま文字に使える**。

#### コントラスト比の実算出

以下はすべて WCAG 2.1 の定義（sRGB 相対輝度）で計算した値である。
アルファ付きの色は地に合成した実効色で計算している。**目視の印象ではなく計算値。**

**ライト（地 = `#FEF5EB`）**

| トークン | 値 | 実効色 | 対 地 | 判定 |
|---|---|---|--:|---|
| `ink` | `rgba(67,69,72,1.00)` | `#434548` | **8.92:1** | AA / AAA |
| `ink2` | `rgba(67,69,72,0.78)` | `#6C6C6C` | **4.87:1** | AA |
| `ink3` | `rgba(67,69,72,0.60)` | `#8E8B89` | 3.14:1 | 大きい文字・アイコンのみ |
| `ink4` | `rgba(67,69,72,0.30)` | `#C6C0BA` | 1.67:1 | 装飾のみ |
| `separator` | `rgba(67,69,72,0.12)` | `#E8E0D7` | 1.21:1 | 罫線 |
| `accent` | `#A85426` | — | **4.92:1** | AA。**文字・リンクに使える唯一のテラコッタ** |
| `accentVivid` | `#D08256` | — | 2.78:1 | **文字禁止。**線・アイコン・インジケータのみ |
| `surface` | `#FFFFFF` | — | 面差 1.08:1 | カード・入力欄 |

`ink` を `#FFFFFF` の面に載せた場合は 9.62:1【計算】。

**ダーク（地 = `#1C1D1F` / 面 = `#26282B`）**

| トークン | 値 | 実効色 | 対 地 | 対 面 | 判定 |
|---|---|---|--:|--:|---|
| `ink` | `rgba(254,245,235,0.92)` | `#ECE4DB` | **13.40:1** | 11.85:1 | AA / AAA |
| `ink2` | `rgba(254,245,235,0.62)` | `#A8A39D` | **6.74:1** | 6.20:1 | AA |
| `ink3` | `rgba(254,245,235,0.50)` | `#8D8985` | **4.86:1** | 4.55:1 | AA |
| `ink4` | `rgba(254,245,235,0.35)` | `#6B6966` | 3.08:1 | 3.00:1 | 大きい文字・アイコンのみ |
| `separator` | `rgba(254,245,235,0.14)` | `#3C3B3C` | 1.51:1 | — | 罫線 |
| `accent` | `#D08256` | — | **5.63:1** | 4.93:1 | AA。**ダークでは原色のまま使える** |
| `accentVivid` | `#E09A70` | — | 7.25:1 | 6.35:1 | 強調 |
| `surfaceRaised` | `#434548`（チャコール原色） | — | 面差 1.75:1 | — | 最上位の面。上に `ink` で 7.86:1 |

> **`surfaceRaised` の上ではアクセントが弱る。**
> `#D08256` を `#434548` に載せると 3.21:1、`#E09A70` でも 4.13:1【計算】。
> 持ち上がった面の上でアクセント文字を使うなら `accentVivid`（4.13:1）を選び、
> それでも本文サイズでは AA に届かないことを承知しておく。

**AA（4.5:1）を満たす最小アルファ**【計算】。トークンを増やすときの上限として使う。

| 組み合わせ | 4.5:1 に必要なα | 3:1 に必要なα |
|---|--:|--:|
| ライト: チャコール on クリーム | **0.75** | 0.58 |
| ダーク: クリーム on `#1C1D1F` | **0.47** | 0.34 |
| ダーク: クリーム on `#26282B` | **0.50** | 0.35 |

**ダークの方が薄いアルファで基準を満たす。**
ライトの二次テキストをダークと同じ 0.62 にすると **3.27:1 で AA を割る**【計算】。
ライトとダークで同じアルファ値を使い回してはいけない。

#### テラコッタを「塗り」に使う場合【計算】

| 文字色 | 地 `#D08256` | 地 `#A85426` |
|---|--:|--:|
| `#FFFFFF` | 3.00:1 ❌ | **5.30:1** ✅ |
| `#FEF5EB` | 2.78:1 ❌ | **4.92:1** ✅ |
| `#2A1B12` | **5.55:1** ✅ | 3.13:1 ❌ |

**`#D08256` を塗りにして白文字を載せる、という一番やりたくなる組み合わせが失敗する。**
塗りが必要なら `#A85426` + クリーム文字にする。
ただし DESIGN.md 第9.2章の「テラコッタは面積を持たせない」に従い、**塗りの使用は最小限にすること。**

### 4.4 「透明度を下げる」設定への対応

macOS には「システム設定 > アクセシビリティ > ディスプレイ > 透明度を下げる」がある。
**これが ON のときに材質を出し続けるのはアクセシビリティ上の後退である。**

**A1 時点で未実装。** 実装（`ChatScreen`）は無条件に本文ペインを塗り、サイドバーを塗っていない。

【推測】SwiftUI 側では `NSWorkspace.shared.accessibilityDisplayShouldReduceTransparency` を見て、
ON のときサイドバーにも不透明な地を敷くのが素直だと思われる。**検証していない。**
要件そのものは有効なので、第10章 #4 に未確認事項として残す。

### 4.5 材質の上で配色を成立させる

材質は「地が固定の色ではなくなる」ことを意味する。**背後の壁紙によって明るさが変わる。**
そのままでは 4.3 節で計算したコントラスト比が保証されない。

**解決策は、ネイティブアプリと同じ構造をそのまま採ること。**
Notes も Mail も、**サイドバーだけが透け、本文ペインは不透明**である。

実装【出典: `Sophia/Sources/UI/Chat/ChatScreen.swift`】:

- 本文ペイン: `.background(SophiaColor.background)` で**塗る**。ここで 4.3 節の比が保証される
- サイドバー: **何も置かない。** SwiftUI では塗らなければ OS の材質が見える

**Electron 時代はこれを「1ウィンドウ1材質という制約の回避策」として書いていたが、
ネイティブではその制約自体が無い。** 回避策ではなく、**可読性のための構造**として採用している。
そのぶん理由が明確になった ─ 文字を載せる面は不透明でなければ比を保証できない、というだけである。

**副次的な利点として性能上も有利である。** 開発機はファンレスで、
生成中は GPU が推論に取られる（[TUNING.md](TUNING.md)）。
ぼかしの面積が小さいほどコンポジットの負荷は下がる。
【推測】具体的なフレーム時間の差は計測していない。

サイドバー上の文字は地が変動するため、**`ink` / `ink2` までに留め、`ink3` 以下を使わない。**

> **実装はこの但し書きを完全には守れていない。**
> `ChatScreen` の footer は、エンジン名とモデル名を `ink2` で出す一方、
> 「エンジン」というラベルと版番号の行に `ink3` を使っている。
> ライトの `ink3` は 3.14:1（4.3節）で、**不透明な地でも本文サイズでは AA を割る値**である。
> 地が変動する材質の上ではさらに落ちる。**【未確認】実機で読めるかは目視していない。**
> 版番号は常時見える必要がある（完成条件8）ので、目視の結果次第では `ink2` へ上げること。

## 5. Apple HIG の数値（AppKit からの実測）

Apple の Human Interface Guidelines のページは JavaScript で描画されており、
自動取得しても本文が得られなかった。**そのため HIG の文章を引用するのではなく、
AppKit の実際の値を macOS 26.5.2 上で計測した。** 以下はすべて【実測】である。

**この章は版 1.0 からまったく変えていない。** 実装（`SophiaMetrics`）が全面的に依拠している一次データである。

### 5.1 コントロールの高さ

【実測: `intrinsicContentSize`】

| 部品 | large | regular | small | mini |
|---|--:|--:|--:|--:|
| `NSButton`（角丸ボタン） | 28 | **24** | 20 | 16 |
| `NSTextField` | — | **24** | 22 | 19 |
| `NSPopUpButton` | — | **24** | — | — |
| `NSSearchField` | — | **24** | — | — |
| `NSButton`（チェックボックス） | — | 16 | — | — |

**macOS のコントロール標準高は 24pt。** Web の癖で 36〜40pt にすると、
それだけで「Mac のアプリではない」印象になる。
ただし Sophia の**送信ボタンなど主要動作は 28pt**（large 相当）でよい。
実装は `SophiaMetrics.controlHeight = 24` / `primaryControlHeight = 28`。

### 5.2 サイドバー

【実測: `NSSplitViewItem(sidebarWithViewController:)` の既定値】

| 項目 | 値 |
|---|--:|
| `minimumThickness`（最小幅） | **140** |
| `automaticMaximumThickness`（自動時の最大幅） | **250** |
| `canCollapse` | `true` |
| `holdingPriority` | 260（本文は 250。**サイドバーが幅を保持する**） |
| サイドバー行の高さ（`NSOutlineView` sourceList） | **24** |
| 階層のインデント幅 | **12** |

→ **Sophia のサイドバーは既定 240 / 最小 140 / 最大 320。**
240 は AppKit の自動最大値 250 の内側に収まり、日本語の会話タイトルも収まる幅である。
【推測】240 という具体値は 140〜250 の範囲から選んだ設計判断で、実測値そのものではない。

実装は `SophiaMetrics.sidebarDefaultWidth / MinWidth / MaxWidth` を
`.navigationSplitViewColumnWidth(min:ideal:max:)` に渡している。
**折りたたみは `NavigationSplitView` の標準挙動**（列ごと消える）であり、
Open WebUI のようなアイコンレールは作らない（UI_SPEC.md 10.1-#2）。

### 5.3 タイトルバー・トラフィックライト

2.3 節の表を参照。要点だけ再掲【実測】:

| 項目 | 値 |
|---|--:|
| 標準タイトルバーの高さ | 32 |
| ツールバー付き（unified）の高さ | **52** |
| トラフィックライトの大きさ | 14 × 14 |
| ボタン原点の間隔 | 23（隙間 9） |
| 3個ぶんの幅 | 60 |

**位置は指定しない**（2.1節）。この表は寸法の基準としてのみ使う。

### 5.4 余白のリズム

**macOS の公式なグリッド数値は公開されていない。**
ただし 5.1〜5.3 の実測値のうち、面と面の関係を決める値
（コントロール高 16 / 20 / 24 / 28、タイトルバー 32 / 52、インデント 12、行高 24）は
**すべて 4 の倍数**である。一方でトラフィックライトの 14 / 9 / 23 や
`NSTextField` の small = 22、サイドバー最大 250 のように、4 の倍数でない実測値も存在する。
**「4 の倍数がリズムの基調」であって「全部が 4 の倍数」ではない。**

| 段 | 値 | 用途 | 実装 |
|--:|--:|---|---|
| 1 | 4pt | アイコンと文字の隙間 | `SophiaMetrics.space1` |
| 2 | 8pt | 関連する要素の間 | `space2` |
| 3 | 12pt | サイドバー行の左右パディング、階層インデント | `space3` |
| 4 | 16pt | ペイン内側の標準パディング | `space4` |
| 5 | 20pt | 段落・ブロックの間 | `space5` |
| 6 | 24pt | 大きな区切り | `space6` |

**【推測】この 6 段は 5.1〜5.3 の実測値（12・16・24・52）から逆算した整理であり、
Apple が公開している数値ではない。**

### 5.5 角丸

**部品の角丸半径について、AppKit は値を公開していない**（`NSBox.cornerRadius` の既定は 0）【実測】。
ウィンドウの角丸だけは非公開 API から **16pt** が読めた（2.6節）。

【推測】以下は macOS 26 の見た目に合わせた提案値であり、**実測に基づかない**。

| 対象 | 値 | 実装 | 状態 |
|---|--:|---|---|
| ボタン・入力欄（高さ 24〜28） | 6pt | `SophiaMetrics.controlRadius` | 実装済み。**純正と並べた確認は未実施** |
| カード・吹き出し | 10pt | `cardRadius` | 実装済み。入力欄とユーザーバブルが共有する（UI_SPEC.md 10.1-#15） |
| サイドバーの選択行 | 6pt | `sidebarRowRadius` | 実装済み。**純正と並べた確認は未実施** |
| ポップオーバー | 10pt | — | A1 に該当部品が無い |
| ウィンドウ | **触らない**（OS 任せ） | — | 指定していない |

> **「実装済み」は「調整済み」ではない。**
> 提案値がそのまま入っているだけで、純正アプリと並べて見比べた記録は無い。
> 第9章の目視確認に残してある。

### 5.6 罫線

`separatorColor` は黒 9.8%（ライト）/ 白 9.8%（ダーク）【実測】。

太さについては AppKit に数値を返す API がなく、**測れていない**。
【推測】macOS の罫線は 1pt が標準である。実装も `SophiaMetrics.hairline = 1`。
`0.5` にすると Retina で 1 デバイスピクセルの髪の毛線になり、macOS より細くなる。

## 7. やってはいけないこと

**OS の見た目を自分で描き直そうとすると、必ず不気味の谷に落ちる。**
以下は「それらしく見えるが、純正アプリと並べた瞬間に偽物とわかる」典型例である。

> 7.2〜7.5・7.7 は CSS でしか踏めない罠だったため削除した。番号は詰めていない（冒頭の改訂表を参照）。

### 7.1 AppKit 風の見た目を自前で描き直す

DESIGN.md および CLAUDE.md で明示的に禁止されている。
理由は「似ているが違う」が最も悪い結果になるため。
自前の再現は OS の更新に追随できず、**新しい macOS が出た瞬間に全体が古びる。**

**SwiftUI でも同じことが起きる。** 標準部品を使わずに `Rectangle` と `Text` で
それらしいボタンやリストを組み上げれば、Electron 時代とまったく同じ失敗になる。
Sophia は「OS が描くものは OS に描かせ、それ以外は Sophia 自身の顔を出す」方針を採る。

### 7.6 Web の寸法感を持ち込む

| Web の癖 | macOS の実測値 |
|---|---|
| 本文 16px | UI は **13pt**【実測】 |
| ボタン高 40px | **24pt**（主要動作でも 28pt）【実測】 |
| 行の高さ 1.5em | body は 13pt に対し **16pt**（≒1.23）【実測】 |
| 角丸 4px または 8px 一律 | 部品の大きさに応じて変える（5.5節） |
| 影で階層を作る | macOS は**面の明度差と罫線**で階層を作る。影はウィンドウとポップオーバーだけ |

**この罠は SwiftUI でこそ踏みやすい。** `.padding()` や `.font(.body)` の既定は
iOS 寄りの寸法感で、macOS の 13pt / 24pt より大きい。**既定に任せず 第5章の値を明示すること。**

### 7.8 アニメーションを足す

macOS のアプリは驚くほどアニメーションが少ない。
ホバーでの色変化は 0.1 秒前後、それ以外は基本的に即座に切り替わる。
Web 的なイージング（0.3 秒の ease-in-out など）を全体に掛けると、**動きが重く感じる。**

実装で明示的にアニメーションしているのは「最下部へスクロール」の 0.15 秒だけである
【出典: `ConversationView`】。**視差効果を減らす設定への対応は未実装**（4.1節）。

## 8. 日本語入力（IME）の作法

**2026-08-16 に、入力欄で日本語が1文字も打てない不具合を作り込んだ**（修正はコミット `c4e28a9`）。
次に入力欄を触る人が同じ穴に落ちるので、原因と作法を残す。
実装は `Sophia/Sources/UI/Chat/ComposerTextView.swift`、
守るためのテストは `Sophia/Tests/ComposerTextViewTests.swift`（10件）。

**この章の3点は、どれも「AppKit と SwiftUI が同じ文字列を別々に持っている」ことに由来する。**
片方の再描画がもう片方の入力途中を壊す ─ 変換中の一瞬しか起きないので、**目で見て気づけない。**

### 8.1 入力欄に `TextEditor` を使わず `NSTextView` を直接使う

**理由は Enter の意味である。**

Sophia は Enter で送信し、Shift+Enter で改行すると決めた（UI_SPEC.md 10.3）。
ところが日本語入力では、**変換を確定する Enter** と**送信する Enter** が同じキーである。
両者を区別できないと「にほんご」を変換中に Enter を押した瞬間、
**未確定の文字がそのまま送信される。** 日本語話者が必ず踏む。

区別に必要な情報は `NSTextView.hasMarkedText()`（変換中かどうか）で、
**これは AppKit にしかない。SwiftUI の `TextEditor` からは取れない。**
だから `NSViewRepresentable` で `NSTextView` を直接抱える。

判定は1か所に閉じている【出典: 実装】:

```swift
func textView(_ textView: NSTextView, doCommandBy selector: Selector) -> Bool {
    guard selector == #selector(NSResponder.insertNewline(_:)) else { return false }
    if textView.hasMarkedText() { return false }          // 1. 変換中の Enter は「確定」
    if NSApp.currentEvent?.modifierFlags.contains(.shift) == true { return false }  // 2. 改行
    parent.onSubmit()                                      // 3. それ以外は送信
    return true
}
```

Shift の判定に `NSApp.currentEvent` を見ているのは、**AppKit が Shift+Enter でも
同じ `insertNewline(_:)` を送ってくる**ため。selector だけでは区別できない。

> **付随して切っている機能**【出典: 実装】: 自動引用符置換・自動ダッシュ置換・
> 自動テキスト置換・連続スペルチェック。**入力欄は利用者が書いた通りを送る場所**で、
> 勝手な置換はプロンプトを静かに変えてしまう。

> **【実測】`NSTextView(usingTextLayoutManager: false)` で TextKit 1 を明示している。**
> macOS 14+ の既定（TextKit 2）だと `layoutManager` が nil になり、
> **入力欄の高さを実測できない**（内容に応じて器を伸ばす仕様が作れない）。

### 8.2 変換中は `textView.string` へ代入してはいけない

**これが今回踏み抜いた罠そのものである。**

`NSViewRepresentable` の `updateNSView` は、SwiftUI 側の状態が変わるたびに呼ばれる。
そこで素直に `textView.string = text` と書くと、**入力セッションが畳まれ、
未確定の「にほん」ごと消える。** 結果として日本語が1文字も打てない。

さらに悪いことに、**変換中でも `updateNSView` は呼ばれる。**
プレースホルダ判定（8.3節）の状態更新が再描画を起こし、そこから来る。
「変換中に SwiftUI が再描画することは無いはず」という前提が誤りだった。

対策はガード1行【出典: 実装】:

```swift
// 変換中（マークドテキストがある）は絶対に代入しない
if !textView.hasMarkedText(), textView.string != text {
    textView.string = text
}
```

> **教訓: AppKit ビューの文字列は「SwiftUI の状態の写し」ではない。**
> 変換中は AppKit 側が唯一の正であり、SwiftUI 側の `text` は**遅れている**のが正常。
> 追いつかせようとすると壊れる。

### 8.3 変換中は `textDidChange` が来ない — プレースホルダ判定は別経路が要る

**マークドテキストは確定した編集ではないので、`textDidChange` が発火しない。**

すると次が起きる。利用者が「n」「i」と打って画面に「に」が見えているのに、
`text` は空のままなので、**プレースホルダ（「Sophia に相談する」）が未確定文字に重なって表示される。**

対策は判定を2本に分けること【出典: 実装】:

- **`text`**（送信する中身）… `textDidChange` で更新する。**変換中は更新しない**
- **`isVisuallyEmpty`**（見た目が空か）… `textViewDidChangeSelection` で更新する。
  **選択位置の変化は変換中でも発火する**ので、未確定の1文字目で拾える

マークドテキストも `textStorage` には載っているため、`textView.string.isEmpty` で
「見た目の空」を正しく判定できる。

> **プレースホルダの表示に `model.input.isEmpty` を使ってはいけない。**
> `ComposerView` は `isVisuallyEmpty` を別の `@State` として持っている。
> 同じ理由で、入力欄の高さ追従（`reportHeight`）も
> `textViewDidChangeSelection` から呼んでいる ─ 変換候補で行数が変わる場合に追いつくため。

### 8.4 この章を壊さないためのテスト

`Sophia/Tests/ComposerTextViewTests.swift` が実物の `NSTextView` を組み立てて検証している。
**`makeScrollView` / `apply` が `Context` を受け取らない形に切り出してあるのは、
テストから入力欄の実物を触るため**である（`NSViewRepresentableContext` は自前で作れない）。

守っている振る舞い:

- マークドテキストが SwiftUI の再描画を跨いで生き残る
- **ローマ字の全打鍵を通しで再現しても壊れない**（`updateNSView` が何度来ても未確定文字が消えない）
- 未確定の1文字目でプレースホルダが消える
- 変換確定でバインディングに文字が届く
- 変換中の Enter は送信しない / 変換していないときの Enter は送信する
- 外からの空クリア（送信後）はちゃんと適用される

**入力欄を触ったらこのテストを必ず走らせること。** 実機で日本語入力が回復したことは
利用者が確認済みだが、**回帰は目で見て気づけない種類の不具合である。**
