## Part A — 予算の分解（監督承認済みの5本）

**目的**: `fixedPreamble = 105` の内訳を実トークナイザで割り、
**#286 の「正しい引き算」を定義できる状態にする。**

### 器の条件

- **R1**: `SophiaDefaults.systemPrompt` / `FolderTool.definitions` / `SophiaMessage.estimateTokens`
  を**すべて本番から import する。** テスト内に文字列も係数も複製しない
- **R2**: 会話は `MLXEngine.chatMessages(for:)` で組む。`container.prepare(input:)` へ
  出荷と同じ `UserInput`（`tools` / `additionalContext`）を渡す
- **R3**: 数えるのは `lmInput.text.tokens.count`。**出荷が通るシリアライズ経路そのもの**

### 測る5本

| # | 測るもの | 取り方 | 何が決まる |
|---|---|---|---|
| A1 | `systemPrompt` **単独** | `[.system(systemPrompt)]` のみ | 二重計上で引く**本当の値** |
| A2 | テンプレート固定分 | **空の会話**との差 | `perMessageOverhead` に渡す値 |
| A3 | **`105` の内訳検算** | `[.system, .user("こんにちは")]` を組み、**A1+A2+（5文字ターン）と一致するか** | **R7。合わなければ以降は読まない** |
| A4 | 栞1行 / 360の読み取り / 6件ターン全体 | 概算と実測を**両方**記録 | **`measuredEstimateGap` の置き換え** |
| A5 | `prepare` 単体の所要 | 会話長を変えて n=3 ずつ | 裁定2の条件1（組み直しの費用） |

**A3 が合わなければ A4 の数字を持ち出さない。** 分解が間違ったまま次の判断へ
入るのが、今日 1.47 で起きたことである。

**A4 は比を1つに丸めない。** 日本語本文／パス／JSON／栞で**別々に出す。**
`1.47` が壊れた理由の半分は、**混成の列に単一のスカラを掛けたこと**にある。

**A5 は `prepare` のみを計る。** `perform` を呼ばない ──
`prepare` はモデルを走らせない（MLX_SWIFT 6.2節）ので、ここに前向き計算が
混じったら器の誤りである。

## Part B — デコード半減の切り分け

### 主張と、いま言えること

引き継ぎの主張は **「デコード 18〜19 → 9〜10 tok/s に半減」**。
BENCH_RESULTS は既に近いことを記録している ── 健全時 19.46/19.21、
別の走行で 16〜18、そして**「今回の走行は decode が 6.9〜10.4 tok/s しか出ておらず
（当時は19.5）、機体はむしろ今のほうが重い」**。

> **つまり相関は既にある。無いのは「圧迫を操作したら半減が付いてくるか」である。**
> **観測だけでは原因を言えない。** 起こせて初めて言える。

### 器は既にある（新しく作らない）

`PrefillProbeTests` が `decode_tps` を既に記録している（:793）。
**新しいハーネスを書かない** ── 書けば「2部＝9GB」の再来を招く（R1 / 0-4）。

### 「同じ会話」の定義（監督の指定への回答）

**次の5つが一致していることを「同じ」と呼ぶ。1つでも違えば別の会話である。**

| 何 | 固定の仕方 |
|---|---|
| 入力の文字列 | `SOPHIA_PROBE_SAME_PROMPT=1`（毎回同じ入力＝**トークン数を固定して交絡を消す**） |
| `maxTokens` | 明示。**デコード率は生成長で変わる**ので、短いと起動費用に飲まれる。**256以上**を薦める |
| 思考の ON/OFF | `SOPHIA_PROBE_THINKING` を明示。ONは `maxTokens` を4096へ引き上げるので混ぜない |
| モデル | `SOPHIA_PROBE_MODEL` を明示（0.6B と本番を混ぜない） |
| **描画後のトークン列** | **`prompt=` が全走行で一致すること。** 一致しなければ会話が同じでない |

**最後の1つが器の検算である（R8）。** `prompt=` がずれた走行は、
**条件が違うのではなく会話が違う。** 比較から外す。

### 手順

| 段 | 条件 | n | R |
|---|---|---|---|
| **B0** | **陰性対照**: Part 0 を満たした静かな機体（常駐1.4GBのみ） | **3** | **R4** |
| **B1** | 陽性対照: 同じ会話・同じ設定で**もう一度** B0 | 3 | **R5**（器に再現性があること。B0とB1が割れたら以降は無意味） |
| **B2** | **圧迫を操作する**: メモリを意図的に占有し、スワップを使わせた状態で同じ会話 | **3** | 半減を**起こせるか** |
| **B3** | 解放して B0 の条件へ戻す | 3 | **可逆か**（戻らなければ圧迫以外の原因） |

**B2 の圧迫の作り方は、監督の裁可を得てから決める。**
2部起動は**使わない**（既知の産物）。利用者の実使用に近いのは
「他アプリを開く」だが、**再現性は落ちる。** ここは設計判断なので投げる。

### 判定

- **B0≒B1 でなければ、以降の差は読まない**（器が揺れている）
- **B2 で 9〜10 tok/s へ落ち、B3 で戻る** → 圧迫が原因と言える
- **B2 で落ちない** → **環境要因説は棄却**。半減の原因は別にある
- **B3 で戻らない** → 圧迫では説明できない不可逆な何かがある

**n=1 で機構を語らない。** BENCH_RESULTS が自分でそう書いている
（「今日の失敗（n=1 で機構を語る）を繰り返さないこと」）。

## Part B 追補 — **判定の閾値（データを見る前に固定した。以後動かさない）**

**確定日時: 2026-08-23、Part B を1回も走らせていない時点。**
**この節を後から書き換えないこと。** 書き換えたら、その走行の判定は無効である。

### 統計の扱い（先に宣言する）

- **各段 n=3。3本の生値を全部並べる**
- **代表値は中央値**（平均は使わない。3本のうち1本が外れたとき平均は引きずられる）
- **平均を出さない**

### 閾値

| # | 決めごと | **数字** | 根拠 |
|---|---|---|---|
| **T1** | **B0≒B1 の許容幅** | 中央値の差が **±10% 以内** | BENCH_RESULTS の健全時 replicate は 19.46 / 19.21＝**差1.3%**。別走行の帯 16〜18 で**約12%**。±10%は雑音を飲むが、半減（50%）は飲まない |
| **T2** | **「半減が起きた」** | B2 の中央値が **B0 の 65% 以下** | 半減＝50%。65%に置くと余裕はあるが、T1の±10%帯からは**十分に離れている** |
| **T3** | **「半減しなかった」＝棄却** | B2 の中央値が **B0 の 90% 超** | T1 の許容幅の外側に置く。**ここに落ちたら環境圧迫説は棄却する** |
| **T4** | **判定不能** | B2 が **65%超〜90%以下** | **「変わったが半減ではない」を独立の結論として先に用意する。** これが無いと、11 tok/s を見て「6.9〜10.4 の幅があるから半減だ」と言える余地が残る |
| **T5** | **「戻った」** | B3 が B0 の **±10% 以内** | **T1 と同じ幅にする。** 違う幅を使うと、戻りだけ甘く判定できてしまう |
| **T6** | **散らばりが大きすぎる** | 1組の中で `(max−min)/中央値 > 20%` | **n を5へ増やす。** n=5 でも 20% を超えたら**「器が対象を測れていない」として中止**し、そう報告する |
| **T7** | **走行の除外** | `prompt=` が他と一致しない走行 | **条件が違うのではなく会話が違う。** 除外して取り直し、**除外したことと理由を報告に書く**（黙って捨てない） |

### 事前に書いておく結論の形（4つしかない）

1. **T2 を満たし、T5 も満たす** → **圧迫が原因と言える**
2. **T3 に落ちる** → **環境圧迫説は棄却。** 半減の原因は別にある
3. **T4 に落ちる** → **判定不能。** 「半減」とは呼ばない。n を増やすか、設計を見直す
4. **T1 か T6 で止まる** → **器が揺れている。** 差は読まない

**5つ目を後から作らないこと。**

### B2 の圧迫 —— **(b) のみ**（監督裁可）

一定量を確保するだけの小さなプロセスを置く。**2部起動は使わない**（57倍崩壊は既知のハーネス産物）。
**(a)（利用者のアプリを開く）は利用者へ上申中。走らせない。**

**確保量も先に決める**: **スワップが実際に使われ始めるまで増やす**のではなく、
**空き（`vm_stat` Pages free）が B0 時点の 1/4 を下回る量**を1回で確保する。
**確保後の生値を必ず添える** —— 「圧迫した」ではなく「これだけ圧迫した」と書く。
