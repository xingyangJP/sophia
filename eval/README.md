# 品質の評価基盤

**適応度関数（品質 ÷ 消費エネルギー）の分子を作るための場所。**
設計は [docs/DESIGN.md](../docs/DESIGN.md) 第15章。

## なぜ要るか

分母（トークン数・秒・メモリ）は測れるようになった。**分子はゼロのままである。**
この非対称を放置すると、**測れるほうだけが最適化される** ──
「8B→4Bに落とす」「量子化を詰める」「system を削る」はどれも分母を確実に下げるが、
**分子がどうなったかを誰も知らない。**

## 原則（破ると意味が無くなる）

1. **絶対評価をしない。対比較にする。** 「80点」は再現しないが「AとBのどちらが良いか」は再現する
2. **目隠しで比べる。** どちらがどの構成かを見せない。期待が判定を汚染する
3. **n=1 で判定しない。** 温度0.7 なら同じ入力でも出力は毎回違う。複数シードで勝ち越しを見る
4. **題材は実際に困っている作業にする。** 綺麗なベンチ問題では差が出ない

## ディレクトリ

| | 中身 |
|---|---|
| `tasks/` | 題材。1タスク1ファイル |
| `runs/` | 実行結果（構成 × シード × タスク）。`[STATS]` を併記する |
| `verdicts/` | **対比較の判定記録。ここが本体。** 過去の判定が積み上がって初めて「前より良くなったか」に答えられる |

## タスクの書き方

`tasks/NNN-短い名前.md` に、下の見出しで書く。

- **prompt** … 実際に送る文
- **判定基準** … 何が良い/悪いのか。**人が読んで判定できる粒度で**
- **自動チェック** … 機械的に判定できるもの（文字数上限、含むべき語、JSONとして妥当か等）。無ければ空
- **備考** … 由来。「いつどんな作業で困ったか」

**一度に揃えないこと。3〜5件から始める。**
完璧な評価セットを作ろうとすると着手そのものが止まる。
