# 001 技術的な調査結果を、自分に向けて解説し直させる

## 由来

**2026-08-18、利用者が実際にアプリへ投げた作業。** 作ったものではない。
Xet 不具合の調査結果（アシスタントが書いた技術文書 400字）をそのまま貼り、
「これを解説して」と依頼した。

**この題材が良い理由: 正解が分かる。** 原文を書いた側が評価できるので、
捏造・反転・埋め草を確実に検出できる。

## prompt

（`eval/fixtures/001-xet-report.md` の全文）＋ 末尾に「これを解説して」

## 判定基準

### 落としてはいけない（内容）

- [ ] 小さいファイルは通常CDN、大きいファイルは Xet 配信、という**切り分け**
- [ ] Xet トランスポートが**無効**だから止まる、という因果
- [ ] 開発機で見えなかったのは**古いキャッシュが残っていたから**
- [ ] **黙って止まる**ことが問題の核心（FR-07 / NFR-10 が未達）

### 書いてはいけない（捏造・反転）

- [ ] **存在しない API を書かない**（例: `@available(*, requires: "Xet")`）
- [ ] **「Swift 6.3.3 は Xet をサポートしていない」と書かない** ─
      6.1以降は**トレイトが効く**から opt-in になったのであり、因果が逆
- [ ] 原文に無い具体性を足さない（例:「無線接続の場合は」）
- [ ] 無関係な定型句を足さない（例:「セキュリティリスクに注意」）

## 自動チェック

- 出力に `@available` を含まない
- 出力に `サポートしていない` と `6.3.3` が同一段落に現れない
- 出力が 2,500 文字以内

## 備考

**この作業で壊れるのは流暢さではなく正確さである。**
出力は日本語として完璧なまま、捏造と反転だけが混ざる。**読んで気づけない。**
量子化・モデル縮小の評価題材として、まさにこの性質が要る。
